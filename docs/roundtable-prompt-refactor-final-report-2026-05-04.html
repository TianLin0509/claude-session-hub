一、整体架构（4 层注入模型）

圆桌 prompt 系统由 4 个层级构成。理解每层的装载时机和AI 可见性是后续所有改动的前提。

层内容位置装载时机AI 可见性
L1 BASE_RULES — 核心规则（你是谁 / 三原则 / 怎么找历史） roundtable-scenes.js:35-79 PTY 启动时通过 --append-system-prompt-file 注入一次 会议全程可见，但 PTY 启动后不可变
L2 房间公约 = COVENANT_GENERAL + 场景叠加 COVENANT_RESEARCH roundtable-scenes.js:152-202 / 207-245 同 L1（拼装在同一个 prompt 文件） 同 L1
L3 每轮 prompt（调度上下文 + 上一轮 + 任务 + timeline 路径） roundtable-orchestrator.js 的 buildFanoutPrompt / buildDebatePrompt / buildSummaryPrompt / buildBriefSummaryPrompt PTY 启动后每轮通过 stdin 写入 每轮独立可见，可随轮次变化
L4 timeline.md — 外置历史 C:\Users\lintian\.arena\timeline-{meetingId}.md 不主动注入 AI 通过 Read 工具按需访问

装配流程

buildSystemPrompt(sceneKey, covenantText)
  └─ L1 BASE_RULES + scene.preset(general/research) + L2 covenant
  └─ writePromptFile() → {meetingId}-prompt.md
  └─ CLI 启动: claude --append-system-prompt-file {meetingId}-prompt.md
  └─ PTY 起来后, 每轮通过 stdin 发送 L3 prompt
关键技术约束（贯穿 P5 决策）：PTY 启动后，--append-system-prompt-file 读取的是启动时的内容；后面修改 prompt 文件，已启动的 PTY 完全感知不到。真正的"会中刷新"必须走 L3 路径，不能靠改 prompt 文件。

二、核心设计理念（贯穿全部 Phase）

1. 准入闸门（Admission Gate）

每个 prompt 层都有显式准入规则，写入代码注释 + unit test 双重防护，防止内容慢慢膨胀回到改造前的状态。

典型例子：L1 准入 3 问（所有场景都需要？每轮值得重复？过期会误导？）；L2 research 准入 3 问（只入 PRESET / 不重 COVENANT / 用户偏好不进 covenant）；GENERAL_PRESET 准入 4 条（不依赖当前轮模式才成立）。

2. 差量层（Differential Layer）

下游层级只承载相对上游的差量，不重写规则。来源 Squirtle 第 6 轮："L2 research 不是第二份说明书，而是 differential layer"。

检查标准（用于审查每条新增内容）："如果这条放在 general 里也成立，它就不属于 research"。

3. 单一真相源（Single Source of Truth）

同一份语义不在多处重复定义。P4 五元组格式从两处独立定义（COVENANT_GENERAL + buildBriefSummaryPrompt）改为结构化 schema + render helper，两处共享。

4. 注入层级匹配功能（Inject Layer ≡ Function）

静态信息走 L1/L2，动态信息走 L3。P2 删除 RESUME_REMINDERS 是因为它的功能已被"L1+L2 重注 + Claude --resume 恢复 PTY 历史"完整覆盖；P5 Arena Memory 必须双路径（启动 L1 静态注入 + 会中 L3 动态 hint），否则会中刷新无法生效。

5. 用户画像不进 covenant（User Profile ≠ Protocol）

P1 关键洞察：用户投资风格"15%/35%/30%/20%"被模型当硬规则反向硬套——这是比 token 更严重的问题。用户偏好必须外置（research-profile.md），covenant 只承载所有用户都适用的判断纪律。

6. 先 0→1 做对的，不做 0→0.5 中间态

P5 节奏判断：Charmander 档 1（启动注入）只解决 0→0.5；Squirtle B 方案（启动 + L3 变更提示）多 ~7 行实施成本但功能完整。优先做对的一步，不分阶段半接入。

7. 先验证再设计（Verify Before Design）

圆桌讨论中三次 grep 推翻假设：P2 发现 getResumeReminder() 是死代码（main.js 调用 = 0）；P4 发现"格式三处"实际是"两处"（summary-templates.json 是 deep-summary 用，与五元组无关）；P5 发现整个 core/arena-memory/ 模块从未被 main.js 导入。

8. 死代码删除原则

RESUME_REMINDERS（直接删，因为重复 L1/L2，无独特价值）vs Arena Memory（复活，因为不重复 L1/L2，有独特价值）—— 判断标准是"是否提供其他层未覆盖的功能"，不是"代码本身是否优雅"。

# 投研圆桌 · 研究纪律（差量层 · 仅写 research 独有约束）

## 1. 证据优先
- 先引用数据，再给判断；二手表述低于原始数据源
- 没数据就明确缺口（"我需要 X 数据才能判断 Y"），不硬编

## 2. 假设分层
- 区分**已知事实 / 推断 / 待验证假设**，不把"可能"包装成"确定"
- 区分**短期催化 / 中期逻辑 / 长期结构**，不混为一谈

## 3. 分歧保留
- 同时保留多条解释路径，不为追求统一结论而强行收口
- summary 时明确"主分歧点"

## 4. 输出格式
- 关键结论先行（推荐 / 不推荐 / 中性 / 观望）
- 量化给数字，定性给参照系；问什么答什么，不套模板
- 圆桌产物是观点不是研报——一次 snapshot 给观点足够，别循环调多个 op 拼"完整研报"

## 红线（任何讨论都要避开）
- 非行业龙头硬蹭概念（无独家技术 / 议价能力证据除外）
- 技术明显走坏（破关键支撑、量价背离）
- 监管 / 财务造假风险

const BRIEF_SUMMARY_FIELDS = [
  ['目标',     '本段聚焦什么任务/问题（一句话，20-50 字）'],
  ['关键事实', '你确认的事实/数据（项目化，最多 5 条）'],
  ['关键分歧', '与他人核心分歧 / 自己的不确定（项目化）'],
  ['当前结论', '倾向判断 + 信心度 0-100%（30-80 字）'],
  ['下一步',   '建议下一轮聚焦什么 / 想问对方什么（30-80 字）'],
];

const BRIEF_SUMMARY_CONSTRAINTS = [
  '不超过 500 字',
  '第一人称',
  '不展开论证',
  '不重复事实细节',
];

function renderFiveElementItems() {
  return BRIEF_SUMMARY_FIELDS.map(([n, d], i) => `${i+1}. **${n}**：${d}`).join('\n');
}

function renderBriefSummaryConstraints(style /* 'inline' | 'list' */) {
  return style === 'inline'
    ? `约束：${BRIEF_SUMMARY_CONSTRAINTS.join('，')}。`
    : BRIEF_SUMMARY_CONSTRAINTS.map(c => `- ${c}`).join('\n');
}
