关键发现：现成的"私聊"机制几乎就是独享模式

项目里 core/general-roundtable-private-store.js + renderer/meeting-room.js 已经实现了完整的"私聊"链路：

关键事实：每家 AI 的 PTY 各自独立

Hub 不主动"喂"消息给被排除的 AI 的 PTY。每家 AI 的"对话历史"=它自己 PTY 内的 native transcript（Claude JSONL / Gemini chat / Codex rollout）。当 Hub 不发 prompt 给某 AI 时，该 AI 的 PTY 仅看到自己之前发的内容，完全不知道用户跟其他 AI 说了什么。

这意味着切回多人时必须 Hub 主动构造一段"上下文摘要 / 历史"喂给被排除的 AI，否则它会一脸懵地按"全新轮次"作答，连用户在聊什么都不知道。

③5 种"切回多人时上下文同步"策略对比

这是整个设计最关键的决策。下面 5 种策略各有取舍，先逐个讲清，再统一打分。

方案 A · 完全黑箱（不告诉其他 AI 任何独享期间的事） 不推荐

做法：独享期间消息进 private store（既有），切回时下一轮 fanout/debate prompt 中不提及独享期间发生过什么。

优点：实现成本最低（0 改动，复用既有私聊存储）；轻量。

缺点：

  • 其他 AI 切回时毫无上下文，可能问"我们在讨论什么？"
  • 用户体验断裂 — "我刚跟 Claude 聊了 5 轮深入分析，现在让 Gemini 也加入，结果它一脸懵"
  • 违反用户期望"既能让其他 AI 快速了解问题背景迅速加入讨论"

结论：这是当前默认行为，不解决问题。

方案 B · 全量回放（把独享期间的全部对话喂给其他 AI） 不推荐

做法：切回时下一轮 prompt 前缀拼接：

## 你刚才不在的对话（共 5 轮）
[Round 1] 用户: ... | Claude: ...
[Round 2] 用户: ... | Claude: ...
...
## 现在用户问大家：[本轮新问题]

优点：信息无损；其他 AI 能精准复盘。

缺点：

  • Token 爆炸：5 轮深聊可能 5000+ token，喂两次（给两家）就 10000+ token，每轮都喂会冲爆 ctx
  • Codex/Gemini 输入长度限制，超长会被截断或拒绝
  • 与"轻量简单"诉求相反

结论：仅在用户特别需要"完整复盘"时按需启用，不能做默认。

方案 C · 被动只读（独享期间消息悄悄喂其他 AI 的 PTY，但要求"不答"） 不推荐

做法：独享期间，user 给 Claude 发的每条消息，Hub 同时静默注入给 Gemini/Codex 的 PTY，prompt 形如：[只读 · 不要回答] 用户对 Claude 说: ...

优点：切回时其他 AI 已自然知道全部上下文，零延迟、零额外 prompt。

缺点：

  • Token 持续消耗：每条独享消息都消耗 N+1 倍 token（N 家旁观者）— 反而比方案 B 更贵
  • 不可控：AI 仍可能主动回答（"不要回答"是 prompt 级约束，不可硬保证）
  • turn-complete 检测复杂：旁观 AI 可能产生输出，干扰 marker 判定
  • 违反"独享"语义：用户以为是独享，实际三家都在听

结论：技术风险高，违反"独享"心智模型。

方案 D · 自动摘要注入（默认） 推荐

做法：

  1. 独享期间消息进 private store（既有）
  2. 用户关闭独享时，Hub 调一次 summary-engine（既有，仅支持 Gemini）让锁定的那家 AI 自己总结："请用 100 字以内总结刚才你和用户的对话要点"
  3. 这段摘要存入 meeting._timeline 作为一条 { sid: 'system', text: '[独享回顾] ...' } 条目
  4. 下一轮 fanout/debate 的 prompt 给其他 AI 时，前缀加：
    ## 你刚才暂时离场，期间用户和 ⚡Slot1 讨论了：
    [摘要 100 字]

    ## 现在用户问大家：
  5. 锁定的 AI 自己不需要这段（它的 PTY 已有完整历史）

优点：

  • Token 经济：100-200 字摘要，比全量回放小 10×+
  • 语义清晰：其他 AI 明确知道自己刚才"不在场"，不会假装看见过
  • 用户透明：摘要存入 timeline，UI 可显示一条"[独享回顾]"系统消息让用户审阅
  • 由锁定 AI 自己总结，最准确（它有完整 native PTY 历史）
  • 复用既有 summary-engine.js（仅需扩展支持 Claude/Codex/DeepSeek/GLM）

缺点：

  • 多一次 LLM 调用（摘要生成）— 大约 1-3 秒延迟
  • 摘要质量取决于锁定 AI 的能力（极端情况可能漏点）
  • 对没接 summary-engine 的家（当前仅 Gemini 支持），需先扩展

降级策略：summary-engine 失败时，自动回退方案 E 让用户选。

方案 E · 切回时弹"上下文范围"选择器 作为方案 D 的高级补充

做法：用户点关闭独享时，弹一个紧凑 toast：

┌──────────────────────────────────────────────┐
│ 切回多 AI · 让其他 AI 看到独享期间的什么？     │
│                                              │
│ ◉ 自动摘要 (推荐, 默认)  · 由 Claude 概括 100 字 │
│ ○ 全量回放                · 完整 5 轮对话喂给其他 │
│ ○ 仅最近 1 轮            · 只补最后一条问答     │
│ ○ 不补                   · 其他 AI 全黑箱进入     │
│                                              │
│         [ 取消 ]   [ 确认切回 ]              │
└──────────────────────────────────────────────┘

优点：用户可控，特殊场景（如想让其他 AI 完整复盘）有出口。

缺点：每次都弹会打扰用户；与"简单"诉求略有冲突。

建议落地方式：默认行为=方案 D（不弹 toast），但提供"高级模式"开关：在切换时按住 Alt 才弹此 toast；或者第一次切回时弹一次"是否每次都问我"，用户选"否"则永久走 D。

D（自动摘要）作为默认行为：用户关闭独享时无感切换，由锁定 AI 自动总结 100 字喂给其他 AI；同时摘要进 timeline 让用户可见。

⑥边界场景与缓解

#场景问题缓解
E1 独享期间 user 主动用 @gemini mention 跳到另一家 语义冲突：独享和 mention 哪个优先？ 独享按钮优先级最高；mention 在独享开启时被 UI 灰显，告诉用户"先关闭独享"
E2 用户独享期间只发了 1 条消息就关闭 1 条对话生成摘要意义不大，反而消耗 token 阈值：私聊轮次 ≤ 1 时跳过摘要生成，直接把那条 user 原话拼进给其他 AI 的 prompt（"刚才用户私下问了 X"）
E3 summary-engine 调用失败（如 Gemini 限流） 没有摘要，其他 AI 切回时仍黑箱 降级：① 让用户选（弹方案 E 选择器）；② 若用户关了选择器，则用"仅最近 1 轮"作 fallback
E4 锁定 AI 是 Codex（无原生 summarize 通道） 当前 summary-engine 仅支持 Gemini 本期扩展 summary-engine，让 Claude/Codex/DeepSeek/GLM 都能调（用 PTY 模式发"请总结"prompt → 等 turn-complete）
E5 用户独享 → 切回 → 又独享，频繁切换 多次摘要堆积，timeline 噪声 UI 折叠：连续多次"[独享回顾]"自动合并显示为"独享 N 段"，点开展开各段
E6 独享期间锁定的 AI session 崩溃 / PTY 退出 relaunchCli 后 PTY 历史丢失，摘要无源 Hub 自己有 private store 备份，可绕过 PTY 直接喂"私聊历史"给重启后的 AI 让它总结；或回退用户选择策略
E7 独享开启后用户切到投研模式 / 其他场景 场景切换是否要保留独享状态？ 保留：soloSlot 持久化与场景无关；切场景不改 soloSlot
E8 多个会议室间共享独享状态？ 不应共享（per-meetingId 才合理） state.json 中 soloSlotByMeeting: { [meetingId]: slotIndex } 而非全局字段
E9 独享期间切回 fanout 立即再独享别家 第二段独享开始时，第一段的摘要还没注入完？ queue 化：摘要生成是 await 操作，期间 toolbar 显示 "切回中..."（disable），完成后才允许新独享
E10 用户在独享期间使用"群策群力"/"总结发言"按钮 这些按钮在独享下灰显，但若用户硬点呢？ JS 层 disabled 属性禁用 + click handler 早返；按钮 tooltip 提示"独享模式下请先关闭独享"
