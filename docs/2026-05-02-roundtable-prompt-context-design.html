TL;DR
  • 方案 0（基线）：当前实现。System 注一次（规则+场景+公约），每轮 prompt 按 mode 分三套，summary 重度依赖 PTY 历史。
  • 方案 A 角色显性化：每轮 prompt 多一段"调度上下文"——明示 AI 当前是主驾还是副驾、本轮谁开口、互相能否看见。
  • 方案 B 会议记忆 Ledger：每轮结束后系统侧自动浓缩成 200-500 字的"轮次记忆"，下游 prompt 注入这个 ledger 替代依赖 PTY。
  • 方案 C 结构化协作流：强约束 AI 按 What/Why/Tradeoff/Open Questions/Next Action 五段式输出，下游按结构 fan-in。

  • 方案 E 用户元命令：上下文组成不智能化，给用户 @debate#3-5 / @summary --full 等元命令，每次手动指定要喂什么。

1. 所有方案共用的两层模型

无论选哪个方案，AI 收到的上下文都分两层。差异只在每层装什么。

第 1 层 · System Prompt（启动时一次性注入）

AI 在 PTY 启动那一瞬就读到，之后整个会议室不变。承载"角色定位 / 协作规则 / 场景预设 / 房间公约"。

第 2 层 · Per-Turn Prompt（每轮触发时注入）

用户在圆桌发言或触发命令时，系统把任务说明 + 历史上下文 + 参考资料拼成一段文字，注入 PTY 让 AI 读。每轮一次。

5 种方案的差异完全在这两层各自装什么。第 1 层在所有方案下变化都不大（最多调整公约文本），主要差异在第 2 层。

额外约束：dispatchMode（all / pilot / observer）正交于 mode（fanout / debate / summary）。dispatchMode 决定本轮"谁开口"——只是过滤发送对象，不直接改 prompt 内容。各方案对这一点处理方式不同（基线完全不告知 AI、方案 A 显性告知、方案 B/D 通过 ledger/标签携带）。

2. 方案 0：基线（当前实现）

方案 0：基线

参照系 已上线
MVP 实现，假设"AI 自己 PTY 上下文连贯"，系统侧只投喂任务说明 + 最近一轮观点

选型动机

每个 AI 占一个 PTY，前面所有轮次它都看过——所以系统侧不需要把历史"再喂一遍"，只需要发"任务说明 + 任务相关的最近一轮参考"即可。这是最简洁、token 用量最低的实现。

关键设计假设：summarizer 自己 PTY 上下文里已经存有前 N 轮全部讨论（含自己的、对方的）。系统侧只需提醒任务、附最近一轮唤起记忆即可。

pilot
仅主驾 PTY 收到 fanout/debate/summary 模板。prompt 内容与 all 模式一字不差——AI 不被告知"本轮只你一个"，它要靠自己 PTY 上下文里"主驾红框氛围"猜出来（实际上 AI 不一定能猜到）。
observer
仅副驾两家 PTY 收到 fanout/debate 模板。prompt 内容与 all 模式一字不差——副驾不被告知"主驾本轮静音"。fanout 模板还在写"独立回答"，副驾可能误解为"独立赛跑"。

优势

  • 实现极简，token 用量最低
  • AI 自然发挥，无任何模板束缚
  • 初期 1-5 轮短会议体验好

劣势

  • 长会议（>15 轮）summary 质量断崖（PTY context 满）
  • debate 不支持跨轮引用（只能用最近一轮）
  • dispatchMode 切换 AI 不知，副驾/主驾角色感知靠猜
  • 跨 mode 衔接靠 BASE_RULES 启动一次注入，N 轮后可能淡忘

4. 方案 B：会议记忆 Ledger（cat-cafe LSM 风格）

方案 B：会议记忆 Ledger

中等增量 推荐 Phase 2
每轮结束后系统侧浓缩成"轮次记忆卡"，下游 prompt 注入 ledger 替代依赖 PTY 历史

选型动机

不能永远依赖 PTY 上下文——长会议（>15 轮）context window 总会满，summarizer 看不到完整历史。把"历史记忆"从 PTY 容器迁移到系统侧 ledger 容器，让 prompt 装配时可以显式控制注入哪些轮、注入到什么粒度。

新引入的概念：每轮的"轮次记忆卡"

每轮 turn-complete 后，系统自动生成一张轻量记忆卡（200-500 字），存到会议室独立的记忆 ledger 里：

# 第 3 轮记忆卡（debate 模式 · 群策群力）
用户输入："考虑下三季报数据"
Claude：维持中性 — 业绩 OK 但估值 PE 38 偏高
Gemini：转推荐 — 三季报营收+18% 超预期，毛利率回升
Codex：维持谨慎 — 同行恒玄科技更便宜
本轮共识：业绩面 OK
本轮分歧：估值是否合理 / 是否切到同行

同基线，但额外加一句"系统会在每轮 prompt 头部注入会议记忆 ledger，请把它当作权威历史"。

pilot 模式
主驾 prompt 中 ledger 自带"第 K 轮 · pilot 模式 · 主驾发言"标签，主驾自然知道当前是被点名独说。
observer 模式
副驾 prompt 中 ledger 包含主驾历史观点（即使本轮主驾静音），副驾仍能看到主驾此前怎么说过。语义自然完整。

核心差异：上下文容器从 PTY 迁移到 Ledger

维度基线（PTY 容器）方案 B（Ledger 容器）
历史长度限制受 PTY context window 限制（~200K tok）受 ledger 注入预算限制（用户可调，比如 6K 字）
历史能否复盘无文件可读，AI 自己 PTY 销毁就丢有独立 ledger 文件，可重启 / 跨设备 / 用户审阅
当 PTY 翻车summary 质量断崖无影响（ledger 独立于 PTY）
多 AI 一致性各 AI 看到的略有不同（自己说的 vs 收到的）所有 AI 看到完全一致的 ledger

优势

  • 长会议（15+ 轮）summary 质量稳定
  • 跨轮引用 / @debate 任意轮天然支持
  • 跨设备 / 重启 / 换号场景下记忆可迁移
  • 用户可在 UI 上审阅 ledger（"AI 怎么记的"），增加可信度
  • 三家 AI 看到完全一致的历史（避免"你说过 X" 互相否认）

劣势

  • 每轮注入 token 增量明显（短会议反而费 token）
  • ledger 质量依赖压缩 prompt 调优（可能漏关键观点）
  • "AI 看的是 ledger 不是原话" 可能丢失语气 / 不确定性 / 隐喻
  • 引入新数据结构 = 新故障面（ledger 写失败、损坏、不同步）

5. 方案 C：结构化协作流（Cross-cat Handoff）

方案 C：结构化协作流

中等增量 不推荐
强约束 AI 按"What / Why / Tradeoff / Open Questions / Next Action"五段式输出，下游 prompt 按结构装配

选型动机

cat-cafe Cross-cat Handoff 模式的迁移：每个 AI 在每轮输出末尾必须给出五段式卡片，下游轮次（debate / summary）系统按"对方的 Open Questions"自动转给当前 AI。让 AI 之间像同事一样"传球"，结构化协作。

第 1 层 · System Prompt 内容

BASE_RULES 改为"五部分输出强约束"——和当前的"本色发挥"理念冲突，所以这是核心理念变更。

# 圆桌讨论规则（结构化协作版）
你和另外两位 AI 是同事，本圆桌按"工业化协作"运作。
每轮输出必须包含以下五段（缺一不可）：

### What
你的核心观点是什么。

### Why
基于哪些事实 / 数据 / 推理。

### Tradeoff
你的观点的代价 / 不适用条件。

### Open Questions
- 你仍不确定的问题
- 想问对方某家的问题（请明示对哪家）

### Next Action
基于本轮，建议下一轮聚焦什么。

优势

  • 跨轮可解析 — 程序能稳定提取 What/Why/Tradeoff
  • 分歧不被 summary 抹平（强制保留）
  • 决策档案天然结构化，便于事后审阅 / 自动化

劣势

  • 每轮 token 增量大（强制写五段，最少 +30%）
  • 首轮 fanout 没有"上一轮对方 Open Questions"——结构化的核心红利被浪费
什么时候才考虑 C：圆桌从"自由讨论"演变为"工业化决策流"——需要把 AI 输出灌到下游程序（决策审计 / 自动建仓 pipeline / ADR 生成）。当前定位是"投研伙伴 / 智囊讨论"，C 的红利无法兑现。

6. 方案 D：标签式知识图谱

方案 D：标签式知识图谱

大增量 远期
自由文本 + 轻量标签 [结论][数据][风险][疑问]，下游按标签精准筛选注入

选型动机

方案 C 太重（强结构破坏自然），方案 B 又太粗（ledger 全文注入费 token）。折中：让 AI 自由文本但鼓励在关键陈述末尾加方括号标签，下游 prompt 装配时按标签筛选——debate 时只注入 [结论][疑问]，summary 时全量注入 [结论][数据][风险]。token 利用率最优。

第 1 层 · System Prompt 内容

基线 + 加一段"建议（不强制）"：

# 协作礼仪（建议，不强制）
为了便于另两家在后续轮次精准引用你的观点，
建议在关键陈述末尾用方括号标签，例如：

兆易创新当前 113.2 处于上方密集区。[结论]短期不建议追入。
三季报营收 27.4 亿同比 +18%，毛利率回升至 36%。[数据]
但限售股解禁压力 8.3% 月底兑现。[风险]
另外想问 Codex：恒玄科技你怎么看？[疑问·@Codex]

可用标签集（自由组合，不打标签也 OK）：
[结论] [数据] [风险] [假设] [反驳] [疑问·@<who>]

7. 方案 E：用户元命令驱动

方案 E：用户元命令驱动

轻量补丁 可叠加
把"该投喂多少历史"决策权完全交给用户，不智能化压缩

选型动机

方案 B/D 的智能压缩 / 标签解析都有失败可能。另一种思路：不要智能化，给用户精细元命令——用户每次发言时显式指定"这轮我要什么级别上下文"。本质上是把 token 预算控制权从系统侧转回用户侧。

第 1 层 · System Prompt 内容

基线 + 一句"用户可能在 prompt 头部用元命令调整你看到的历史"。

第 2 层 · Per-Turn Prompt 由用户元命令驱动

用户输入系统装配的 prompt
@debate 同基线（最近一轮另两家观点）
@debate#3-5 注入第 3、4、5 轮另两家观点（跨轮引用）
@debate --brief 另两家观点压缩到 500 字内（用户主动省 token）
@summary @Claude 同基线（依赖 PTY 历史）
@summary @Claude --full 显式注入全部历史轮（不依赖 PTY）
@summary @Claude --recent 5 只注入最近 5 轮
@summary @Claude --bullets 只注入要点列表（极简）
@pilot --silent 主驾发言时不告知"另两家静音"（保持主驾自然）

系统侧不智能压缩，只按用户指令执行。所有 ledger / 标签 / 五段式都不引入——上下文组成完全由用户元命令决定。

优势

  • 极致透明 — 用户清楚每轮注入了什么
  • token 用量完全可控
  • 无智能化失败（没有"压缩漏关键观点"风险）
  • 可与方案 A 无冲突叠加（A 提供基础， E 提供精细控制）

劣势

  • 使用门槛高（用户需要记元命令）
  • 新手不友好（默认体验等于基线，没有改进）
  • 智能化收益放弃（系统不主动帮用户优化）
  • 不解决"系统侧能不能持久化复盘"——记忆仍在 PTY 容器里
定位：E 不是单独走的方案，是叠加在 A 之上的精细控制层。先用 A 解决角色显性化，再开放 E 的元命令给重度用户用。

9. 需要你决策的核心问题

  1. 圆桌"性格"问题：你期待的圆桌更像哪一种？
    (a) 自由讨论 — 三家随性发挥，自然语言对话（基线 / A / B / D / E 路线）
    (b) 工业化协作 — AI 之间像同事一样按结构传球，便于程序解析（C 路线）
    → 答 (a) 直接砍掉 C；答 (b) 重点考虑 C
  2. 上下文容器问题：长期记忆放哪里？
    (a) 一直依赖 PTY 上下文（基线 / A / E 不引入新容器）
    (b) 系统侧独立 ledger（B 路线）
    (c) 不记忆，每次让用户手动指定（E 路线）
    → 这是方案分组的最关键分水岭
  3. 智能化 vs 用户控制问题：上下文裁剪谁说了算？
    (a) 系统智能压缩 / 标签筛选（B / D 路线）
    (b) 用户元命令显式控制（E 路线）
    (c) 都不要，每次塞全部（基线 + B 暴力版）
    → 决定 D 和 E 哪个更适合你
  4. 角色显性化范围：observer 模式下副驾应不应该看到主驾历史观点？
    (a) 不看 — 副驾独立思考更纯粹
    (b) 看 — 副驾能呼应 / 反驳主驾立场
    → 决定 A / B 在 observer 模式下注入什么
  5. 实施节奏：先做哪个？
    (a) 先 A（最快见效，解决你直接观察到的问题）
    (b) 直接上 B（一步到位，改造长会议体验）
    (c) A + E 同步（基础 + 精细控制）
    (d) 暂不动，再观察现状一段时间
    → 决定下一步行动
