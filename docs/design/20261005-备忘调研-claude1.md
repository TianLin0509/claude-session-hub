## 0. 一页结论（先看这里）

1. **最小字段**：业界共识只有 5 个——标题、原文/备注、创建时间、到期/提醒时间、状态。分类、标签、优先级、关联人、项目都是「有更好」，AI 助理场景可以先不做，或由 AI 自动填、用户不用管。
2. **状态**：主流是「未完成 / 已完成」两态，再加一个「不做了」（TickTick 叫 Won't Do，Things 叫 Canceled）。「推迟」在主流产品里**不是一个状态**，而是**改日期**（推到具体时间）或**换分区**（移到 Someday/以后）。
3. **灵感和待办**：主流做法是**同一个入口收进来，先不分**（Things Inbox、Todoist Inbox、Drafts Inbox、flomo「先记录后整理」），AI 产品再在后台自动归类（Apple Reminders 自动分组、Mem 自动建议 Collection）。没有一家要求用户在说话时就选「这是灵感还是待办」。
4. **清单呈现**：按「时间」分组是共识——今天 / 即将 / 无日期（以后）/ 已完成（折叠或单独页）。防膨胀靠三招：已完成自动藏起来、过期条目不标红而是顺延、长期没动的自动归档。
5. **每日推送**：TickTick 有现成的「每日通知」（固定时间推一次今天的任务概览，可选星期几）；Sunsama 有晚间「收工仪式」逐条决定「改期 / 交出去 / 删掉」。
6. **AI 标题 + 原话**：Mem、AudioPen、Notion AI 会议记录都是「整理稿在上、原文/录音折叠在下」。AudioPen 被诟病「默认不给逐字稿，数字和人名会被抹平」，这正说明原话必须保留。
7. **自然语言改清单**：Gemini（改日期、标完成、删除，但**不支持批量**）、ChatGPT Tasks、Mem Chat、Saner.ai 都已经做到；Todoist Ramble **只能改本次刚说的，不能改已有任务**。

## 2. 重点问题逐条回答

### 2.1 条目的最小字段集合

| 字段 | 业界情况 | 本需求建议 |
|---|---|---|
| 标题 | 全部产品都有 | **必须**，由 AI 提炼，可被用户改 |
| 原文 / 备注 | Todoist、Apple、Google Tasks 都有「备注/描述」；AI 产品（Mem、AudioPen、Notion）额外保留逐字稿或录音 | **必须**，存用户原话，只读不改 |
| 创建时间 | 所有产品后台都有，多数界面不突出 | **必须**，详情页显示 |
| 到期 / 提醒时间 | 共识，但 Things 把「何时做」和「截止」拆成两个 | **一个字段就够**（提醒时间），可空 |
| 状态 | 共识（至少完成/未完成） | **必须**，见 2.2 |
| 分类 / 标签 | 普遍有，但都是可选 | **可省**，或由 AI 自动打一个粗分类（待办/灵感），用户不用维护 |
| 来源（语音/文字、电脑/手机） | AI 产品会记录（Mem 挂音频附件），传统产品不显示 | **建议保留**，几乎零成本，排查和信任都有用 |
| 优先级 | Todoist、TickTick 有 4 级；Things、Microsoft To Do 没有显式优先级 | **可省** |
| 关联人 / 项目 | 项目普遍有，关联人主要在协作产品 | **可省**，原话里自然包含 |
| 重复规则 | 主流都支持 | 首版可省，日后需要再加 |
| 推迟次数 / 最后更新时间 | 界面一般不显示，但 Sunsama 的自动归档实际依赖「连续顺延天数」 | **建议后台记录**，用于后面的「过期处理」 |

**[推断]** 共识最小集 = 标题 + 原文 + 创建时间 + 提醒时间（可空）+ 状态。后台补「来源」和「推迟次数/最后变动时间」两项。

### 2.2 状态设计

- **主流状态**：未完成、已完成；再加「不做了/取消」（TickTick Won't Do、Things 的 Canceled，都和已完成一起进归档区）。
- **「推迟」不是状态，是动作**。业界两种做法：
  1. **推到具体时间**：Todoist「Reschedule」、Apple 通知稍后提醒（1 小时后 / 今天下午 / 明天）、TickTick 3 个预设。改的是日期，状态仍是「未完成」。
  2. **移到「以后」分区**：Things Someday、GTD Someday/Maybe。条目从日常视图消失，只在定期回顾时出现。
- **归档**：Things Logbook、Drafts Archive、Sunsama Archive，都是「从眼前拿走但不删除、能找回」。Sunsama 的自动归档是对「一直推不动」条目的兜底。

**[推断] 建议**：对用户可见 3 个状态——**待办 / 已完成 / 不做了**。「推迟」实现为改提醒时间（有具体时间）或设为「以后」（无日期）。如果界面必须显示「推迟」字样，用一个小标记（如「已推迟 2 次」）而不是独立状态，否则会出现「推迟」和「待办+未来日期」两种表示同一件事的歧义。

### 2.3 灵感和待办是否分开

- **入口不分**：Things Inbox、Todoist Inbox（Ramble 默认进 Inbox）、Drafts Inbox、flomo「先记录后整理」——用户说话时不需要做分类判断。
- **存储和视图上会分**：
  - 传统做法：靠用户「处理收件箱」时手动分（GTD）。
  - Google 的做法：笔记在 Keep、待办在 Tasks，提醒统一归 Tasks。
  - AI 做法：Apple Reminders 一键自动分组、Apple「建议提醒」从文本里抽待办（用户确认才加入）、Mem 自动判断意图并建议分类、Saner 自动从邮件文档抽任务。
- **[推断] 建议**：同一个清单、同一种条目，AI 自动打「待办 / 灵感」一个粗标签。有时间或明确动作的算待办；没有动作的算灵感，默认放进「以后/灵感」分组，不参与每日推送的催办部分，只在推送末尾带一句「今天还记了 N 条灵感」。用户可一键改标签。

### 2.4 清单呈现与每日回顾

- **分组**（共识）：今天（含过期）→ 即将（未来几天）→ 无日期 / 以后 → 已完成（默认折叠或单独入口）。Things 的 Upcoming 把「未来 7 天」单独列在顶部。
- **排序**：组内按提醒时间升序；无日期组按创建时间倒序（最新在上）。Todoist 允许按项目/日期分组排序，但对简洁需求没必要开放。
- **防膨胀**：
  1. 已完成和「不做了」自动移出主视图（Things Logbook、TickTick「已完成和不做」）。
  2. 过期不标红、不单独开「过期」大分组，而是并入「今天」顶部（Things 自动顺延；Todoist 有过期分组但配一键重排按钮）。
  3. 长期没动的自动收起：Sunsama 连续顺延 4 天自动归档并告知数量；Microsoft To Do My Day 每晚清零、次日以「建议」形式再给你挑。
- **每日推送**：
  - TickTick「每日通知」：固定时间、可选星期几，内容是今天完成和未完成的概览。
  - Sunsama 晚间收工：逐条三选一（改期/交出/删）。
  - **[推断]** 你的 21:00 推送可以把两者合一：先一句话总结（今天完成 X 条、还剩 Y 条待办、新记 Z 条灵感），再列明天有提醒的条目，最后列「过期/推了好几次」的 1～3 条，问一句要不要改期或放弃。用户直接回一句话即可处理，不需要按钮。

### 2.5 AI 提炼标题 + 保留原话

- **Mem**：整理好的笔记在上，**录音和逐字稿作为附件挂在底部**，点开可看 [官方]。
- **Notion AI 会议记录**：Summary 和 Transcript 两个标签页 [官方]。
- **AudioPen**：整理稿在上，「Original transcript」在下，可重写；但默认不给逐字稿，被评测指出数字、人名会失真 [评测]。
- **Voicenotes**：转写 + 一句话摘要，可再改写成待办等 [官方]。
- **Reflect**：转写直接追加进当天日记，处理后删除音频 [官方]。
- **[推断] 建议**：列表只显示 AI 标题（一行）；详情页显示原话（逐字、只读）+ 记录时间 + 来源。如果用户手动改了标题，就以用户版本为准，AI 不再覆盖。录音是否保留视隐私和存储决定，**文字原话一定保留**。

### 2.6 用自然语言操作清单的先例

| 产品 | 能做什么 | 限制 |
|---|---|---|
| Google Gemini | 改名、改日期（「把牙医任务改到周四」）、标完成、删除、查看 | 要能明确指认是哪条；**不支持批量**；可能幻觉 |
| ChatGPT Tasks | 对话里建和管理定时任务，另有管理页 | Beta 期最多 10 个活动任务 |
| Mem Chat / Voice Mode | 用语音或对话更新、修改已有笔记 | 偏笔记，不是待办状态管理 |
| Saner.ai（Skai） | 对话建任务、设提醒 | 公开资料细节少 |
| 豆包 / Kimi | 对话建提醒或定时任务 | 改已有条目的能力公开资料不清楚（未验证） |
| Todoist Ramble | 本次会话内「其实我是说…」「删掉那条」 | **不能改已有任务** |

**[推断]**「第 2 条推到周五」这种**按序号指认**依赖用户看到的列表编号，各家都没有把它作为正式特性写进文档。要支持，就要保证推送里和界面上的编号一致且稳定（比如按当次推送快照编号），并在执行后回一句「已把『XXX』推到周五 10/9」让用户确认指对了。Gemini 明确要求「能指认是哪条」，说明模糊指认是业界公认难点。

## 3. 最值得借鉴的设计（5 条）

1. **一个入口、AI 后台归类**（Things/Todoist Inbox + Apple/Mem 自动归类）：用户只管说，AI 判断待办还是灵感、有没有时间；判断错了一句话改回来。
2. **「容易改」优先于「一次说准」**（Todoist Ramble 团队原则）：每次写入后用一句话回显「已记：XXX，周五 10:00 提醒」，说错就直接纠正。
3. **推迟 = 改时间或放进「以后」**（Apple 稍后提醒 / Things Someday）：不新增「推迟」状态，避免状态含义重叠；推迟选项给出**具体时间**（iOS 26.5 的改进）。
4. **过期不惩罚、久拖自动收起**（Things 顺延、Sunsama 连续 4 天自动归档并告知数量）：清单不会越积越长，用户不被红色过期吓到；归档可找回。
5. **每天一次汇总，而不是零散催促**（TickTick 每日通知 + Sunsama 收工仪式）：21:00 一条推送，摘要 + 明天要做 + 1～3 条「要不要放弃」，用户回一句话处理。

## 4. 应避免的坑（3 条）

1. **只给 AI 整理稿、丢掉原话**：AudioPen 被批评数字、人名、原措辞被抹平。备忘恰恰常含人名、数字、版本号，原话必须可查。
2. **状态和分区太多**：「待办/推迟/稍后/以后/搁置」并存时，用户不知道选哪个，AI 也容易判错。Things 的做法是每条只有一个时间状态，宁少勿多。
3. **通知太多或要用户在通知里多步操作**：调研显示多数用户几天内就关通知。只保留「到点提醒」和「每晚一次汇总」两类；自然语言批量操作（「这几条都推到下周」）各家都没做好（Gemini 明确不支持批量），首版宜逐条确认，不要一句话静默改多条。
