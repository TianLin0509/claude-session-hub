- Claude 使用 `InstructionsLoaded` 只读事件，校验 native session ID，拒绝子 agent 和别的原生身份；不参与运行状态判断。加载事件不含正文，点开后明确标“当前磁盘内容，非当时快照”。本机 2.1.269 已用真实 CLI + localhost 回应验证事件及 `@AGENTS.md` 导入；未调用云端模型。
- 原生历史证据按 native identity 保存，表示本会话曾加载，不承诺压缩后还完整存在；Hub 提交快照仍限制为当前 epoch。两类证据分别显示。
- 文件库 worker 读取已知会话和工作区注册表，按生成标记与 `seed-sha256` 分为独立、未改、手改、未知。未改副本按来源和正文折叠，手改/未知单列。无活动 session 也可查看。
- `node scripts/audit-memory-rules.js --data-dir <Hub数据> --home <home> --workspace-root <工作根> --out <输出目录>` 输出只读 JSON/HTML 迁移清单。未改不等于可直接删除：旧会话、来源变更、边界标记必须先核实。此版本不自动删除或改写存量规则，不强制同步存在差异的全局正文。

## 数据与运行

- 原生文件仍由现有 `memory-inspector` 按 provider、profile、工作目录发现，只读浏览。列表的“预计加载”和“可按需读取”不等于运行时注入证明。
- 造梦候选来自昨日之我 SQLite 的 sessions/docs；导出使用同一个只读事务快照，JSONL 分文件但不再截断已经存储的正文。源索引自身的截断/附件缺失不会被修复，过期素材须先刷新。
- 造梦数据放在 Hub 数据目录 `memory/<项目路径哈希>/jobs/<任务ID>/`，含 `input/manifest.json`、素材 JSONL、`prompt.md`、`output/`。这是单次任务快照，不是第二套原始会话档案。
- Git 主目录与已登记 worktree 共用项目记忆。未使用 Git 的目录以会话工作目录分组，子目录会话归入该目录；不会扫描聚合根来猜测归属。
- 造梦 session 的 cwd 是任务目录，purpose 为 `memory-dream`；它使用现有原生会话/审批/停止/恢复机制，素材 session 不被打开。页面展示选中的素材、真实模型/档位、阶段与等待状态，不编造完成百分比。
- 正常完成后校验 `result.json` 的完整清单、索引长度、相对链接和文件边界，再发布到独立 `versions/<版本>/`，最后原子切换 `current.json`。AI 的处理清单是其完成声明，不代表 Hub 审计了每次文件读取。失败不更新已整理游标，原生文件不在落盘目标中。
- 同项目只保留一个未结束造梦；异常在实体 session 内处理，补齐后自动或手动核对保存。已完成任务发布一次，后续修改通过新一轮造梦纳入下一版本。
- 只有用户在输入框亲手发送的消息附带短索引（renderer 显式传 `memoryIndex:true`，由 `session:send-prompt` 处理）。群聊派发、会议、初心、补充发言等自动 prompt 经 `sendToPty` 原样发送。每个原生会话身份/epoch、每个版本发送一次；相同提交编号重试复用原始索引快照。正文由 agent 根据索引内路径按需读取。
- 索引外壳带 `ref="<提交编号>"`。确认发送看原生回显里的 ref 与索引正文（忽略空白差异），不要求逐字节一致，兼容会规整空白的 CLI。
- 运行时没有统一的压缩信号：已发送后上下文用量跌破观察峰值的一半（峰值 ≥40k tokens）即视为已压缩，下次用户消息重新附带索引，记录 `reason:"compacted"`。每会话发送记录最多保留 30 条。
- 上下文页展示确切发送快照；“已发送”不表示模型当前仍保留整段上下文，也不表示主题正文已读取。聊天卡片仅折叠索引显示，原始提交与历史内容保留全文。
- 聊天记录 md：昨日之我每次重新解析一个来源，就在 Hub 数据目录 `transcripts/<来源 key 哈希>.md` 原子重写一份只含对话的记录（工具调用每条一行摘要，不含工具输出）。文件名只取决于来源 key，改标题不影响分享路径；文件丢失会在下次刷新时重建。它是派生导出，搜索仍走 SQLite。聊天记录属于历史导出，不列入已注入上下文。
- 造梦素材改为 md（每条前有 `<!-- event:<id> -->` 注释供引用），prompt 另附各素材会话的完整聊天记录路径，需要更多上文时只读查阅。
- Claude 记录改为流式读完整文件（此前只读尾部 4MB），按信封前缀丢弃 tool_result 行；Claude 与 Codex 一样不受 8MB 文件、1M 字符上限限制。Codex 对话 doc 的 ordinal 改用 rollout 行号，与工具 doc 同一尺度。群聊、Gemini 单文件 JSON 上限提到 64MB。解析版本号已升，合入后首次刷新会重新解析全部来源。
- 附带的索引在建搜索索引时被剥掉（`synthetic-user-filter` 的注入块），因此不会出现在昨日之我搜索里，也不会成为下一轮造梦素材。
- 增量整理：发布时按版本写 `processed/<会话哈希>-<版本>.json`（已整理的 event_id），`current.json` 的 `processed[key]` 记 `{signature,count,file}` 并随原子切换生效。续聊的会话只导出新记录，外加紧邻其前的最多 6 条已整理记录（标 `context:true`，只作上文）。失败不推进。
- 聚合目录（`C:\AIWork`、家目录等非 Git 目录）作为一个项目共享一份梦境索引，这是有意的：索引是导航表，agent 自行挑选相关条目。扫描项目文档改为异步，跳过隐藏目录、AppData 和无权限目录，最多 500 个文件 / 4000 个目录；家目录、盘符根、`C:\Vibe` 只列顶层。文件库在后台 worker 中遍历已知 provider/profile 与项目，按真实路径去重。
- 群聊没有单一当前 session，入口提示先打开成员会话；成员会话与普通会话共用上下文页。记忆页面内不增加会话列表。

## 昨日之我的检索口径

- 只索引自然语言：工具调用只留 ≤120 字符元信息，不进 `docs_fts` / `docs_cjk`，搜索范围只有标题、我的提问、AI 回答；旧请求里的 `tool` 被忽略。
- 依据：改动前工具文本占索引正文 88%，常用词 `session` 要多扫 7.7 倍命中（555ms vs 74ms，热缓存实测）。
- 工具 doc 连规范化副本都不存（`normalized_text` 置空），它只为检索存在。
- `SCHEMA_VERSION=2` 会丢弃旧库并 `VACUUM`（生产库 8.5GB 中 4.2GB 是空闲页），合入后首次启动重建索引。
- 真实数据实测（4346 个会话全量重建，257 秒）：库 8523MB → 880MB，全文索引 3206MB → 154MB；`session` 267ms → 42ms、`worktree` 80ms → 5ms、`SuperRAN` 61ms → 5ms（同机热缓存）。命中数反而略增，因为 Claude 早期正文补回来了。

## 2026-09-19：原生注入证据

- `memory-native-context` 在 worker 中只读取当前 session 已绑定的原生记录路径，核对 native ID；不会枚举文件库，也不打开/恢复原生会话。
- Codex 的 `response_item` 中，user 角色的 `# AGENTS.md instructions for … <INSTRUCTIONS>` 与 developer 角色的 `## Memory` 是当前支持的证据形态。Memory 只显示记忆指令和摘要部分，不把同条消息后面的技能清单混进记忆。
- 每项显示最近一次记录的正文、来源路径和行号。不是当前磁盘文件，也不代表压缩后仍完整保留；检测到压缩时提醒这一边界。
- 相同文件版本复用缓存；文件增长时先校验旧字节前缀的 SHA-256，确认未被原地重写后仅解析新增完整记录。校验需要在 worker 中顺序读取旧字节，但不重复 JSON 解码、保留大工具输出；重写/截断/替换时重新解析。显式刷新强制重读。并发请求合并，缓存最多 8 条会话；超时、身份不符和格式错误明确显示。
- Hub 回执与原生注入错误隔离：一方损坏时展示警告，另一方有效内容仍可查看；不会改写或删除损坏的用户数据。
- 读取器从记录前缀排除工具输出与普通对话，避免图片大行进入 JSON 解码及内存。未写完的尾行留到下次重读。
- 没有 Hub 梦境发布/回执时，仍应显示原生证据。对应单测和真实隔离 GUI 覆盖此场景。
