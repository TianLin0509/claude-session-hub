# 首条消息的卡片连续性

2026-10-14 用户反馈：新建会话发送第一条消息后，欢迎页切成卡片，又闪回欢迎页，约一两秒后才恢复卡片。

## 根因与范围

`16a958f3`（2026-09-12）引入会话卡片缓存时，用 Hub 会话、提供方、运行后端、原生编号和记录路径的完整快照判断是否仍为同一份历史。新会话的原生编号及记录路径可能在发送之后才补齐。原来的严格比较把“首次绑定”也判为“切换记录”，清空已经显示的本地消息卡；此时空的历史快照又生成欢迎页，直到后续记录落盘刷新。

这是界面历史缓存失效问题，不是模型重发或真正退出会话。隔离 Hub 中使用真实发送按钮，注入首次绑定和延迟记录回写，可稳定重现这条链路。

## 修复

- 同一 Hub 会话、提供方和运行后端，原来未知的原生编号或记录路径首次补齐时，继续使用现有卡片与加载状态。
- 已经明确的编号或路径被替换、清空，或者切换会话、提供方、运行后端时，仍使缓存失效。
- 离开后缓存的视图也遵守同样规则；首次绑定本身不会把尚未完成的历史加载标为完成。
- 不修改消息提交、送达确认、原生记录解析和真实用户卡去重逻辑。

## 防回归与证据边界

- `node --test tests/unit-card-history-views.test.js tests/unit-card-view-async-session-guard.test.js tests/unit-prompt-submit-ui-contract.test.js`：首次绑定、逐字段补齐、缓存恢复、真正替换的隔离，以及异步视图归属和提交入口。
- `node tests/e2e-first-send-stability-cdp.js --baseline`：修复前的隔离 Hub，Claude、Codex、Gemini、Kimi、DeepSeek 共 5 类都重现卡片消失和欢迎页闪回。
- `node tests/e2e-first-send-stability-cdp.js`：真实隔离 Hub 点击发送，DOM 变化观察与逐帧采样；绑定后故意延迟 1.8 秒回写，期间消息卡始终可见，权威记录到达后只保留一张用户卡；后台/卡片往返仍保留内容。
- CLI、送达回执和延迟记录使用本地夹具；不声称测试了真实模型推理或当前生产进程。测试的目标是确定性复现并约束 UI 的异步时序。
