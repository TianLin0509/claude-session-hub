# 助理会话状态与侧栏一致

助理汇报会话状态时使用 Hub 的状态和未读信息，业务进展仍读取目标会话的自然语言答复。两类事实分开：运行中不是业务完成，未读不是等待用户决策。

## 来源与传递

1. 侧栏与助理共用 `core/session-sidebar-state.js`，保留原有运行真值、群聊工作心跳、等待输入和未读规则。
2. PTY 窗口持有最新的注意力信息。每次侧栏刷新，由同一会话集合生成状态快照；通过 `assistant:session-view` 只传发生变化的行及被移除的编号。
3. 助理只接受本窗口已知会话的快照，并核对原生会话编号。切换原生身份时旧快照失效，未打开的历史不会拿旧运行/未读状态冒充当前状态。快照不改变 SessionManager 的运行信息，不触发 CLI 操作。
4. 当前工作台、Markdown 档案、`list_sessions` 与本轮冻结资料都使用同一状态；读取/清除未读也会改变档案版本，不必等新回答。

## 字段含义

- `openedCount`：当前已打开并列入完整清单的会话数。
- `activeCount`：其中正在运行或等待输入的会话数。
- `hubState.isActive`：按侧栏共用规则是否活跃。
- `hubState.hasUnread / unreadCount`：是否有未读及未读条数；不表示用户一定需要决策。
- `hubState.needsUserInput`：当前确实在等输入。
- `hubState.source`：最新侧栏快照；尚未同步时以主进程共用规则作为后备。

群聊成员按成员自身状态汇报，计数按会话，不能把成员数当侧栏群聊条目数。活跃分组的逻辑不随“今天/3天”筛选改变，助理不复制个人筛选和时间分组。

## 模型设置

本改动保持用户手动设置。日常问进展、定位和派工建议先试 gpt-6.1-sol 的 low；需要更快时可在该会话使用原生 `/fast`。复杂跨项目规划可临时提高思考深度。轻量模型是否适合作为固定管家，需要另测会话定位和派工准确率，不能只按响应速度决定。

## 验证

`tests/unit-assistant-session-state.test.js` 覆盖空闲、运行、等待、异常、休眠未读、历史未知、读后增量更新、主进程旧计数被真实侧栏快照纠正、原生身份变化及增量传递。

`tests/e2e-assistant-session-state-live.js` 在独立临时数据及 home 中使用当前 Hub 所选订阅账号的真实 Codex PTY；通过普通输入框发送真实任务，观察侧栏与助理的运行、完成、未读条数及读后变化，再检查模型实际收到的冻结资料和自然语言回答。会话创建仅作为测试准备使用工厂入口；不是创建 UI 的端到端验收。
