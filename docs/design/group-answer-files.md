# 群聊回答文件：Hub 只和 Markdown 交互

2026-09-30 用户拍板。

## 为什么

原先卡片内容由 Hub 从各家 CLI 的 transcript 里提取，必须先回答「这段话属于哪一轮」。用户在成员自己的会话里补救、Hub 中途异常或重启时，这种绑定就断了，只能手动「同步」。改为成员把要发到群里的话写进文件后，文件路径本身就标明了「哪个群、第几轮、谁」，不再依赖那一轮是不是 Hub 派出去的。

## 规则

- 回答文件路径：
  - 普通群聊：`<数据目录>/task-docs/<群>/answers/turn-<n>/<成员>/回答.md`，派发提示词末尾附一句路径说明。
  - 工作流轮次：直接用该步的交付文件。`已交付` / `需返工` / `阻塞` 视为已交，`草稿` 显示为「草稿」。
- 卡片只有两态：有内容，或「还没交」。不显示思考中、收取中、同步等 transcript 状态。异常看左侧栏的会话状态，用户进对应会话处理。
- 登记了回答文件的成员，transcript 结果只更新运行状态和凭证，不写正文。下一轮的群聊上下文同样取自文件内容。
- 文件随时更新随时生效：中断前后、Hub 未派发的补救、Hub 关闭期间都算。已接纳的工作流交付仍受交付协议的哈希固定约束。

## 检测

- `main/groupchat/answer-file-monitor.js` 订阅任务目录事件，按群核对最近 30 轮。
- 另有 15 秒一次的慢速巡检，只覆盖 24 小时内活跃过的群，用来兜底丢失的目录事件。
- `groupchat:get-state` 返回前核对一次，覆盖 Hub 关闭期间的变化。

## 重新发送（2026-10-01）

成员因 CLI 异常没收到本轮问题时，卡片上直接点「重新发送」（已交的卡片放在「更多」里）：
- 普通群聊：只把本轮原问题发给这位成员，沿用同一轮、同一个回答文件，发出即返回，不等其他成员、也不等它答完；写好文件后卡片自动更新。接口 `groupchat:resend-member`。
- 成员仍在运行或等待确认时先确认，避免重复做；旧协议群仍用原来的「重试」。
- 工作流群走引擎的「提醒未交付成员」（`delivery:continue`），由引擎核对后补发。
- 不再需要「重新提取」：卡片只认文件。普通群聊也不需要「跳过」：没交不挡下一条消息。

## 工作流逃生：跳过

「流程详情」里可以跳过未交付的成员：

- **跳过协作成员**：Hub 自己记一笔「用户已跳过」，不代写交付。下游成员的提示词会写明该成员被跳过、没有交付。
- **跳过开发流某一步的负责人**：本次任务结束，不合并。
- 跳过之后，该成员再交的文件不会被重新采纳。

## 范围与开关

- 适用范围：普通群聊和逐成员交付工作流群。
- 旧协议群（仍在跑旧任务、尚未迁移）继续用 transcript 提取。
- `meeting.answerSource = 'transcript'` 是单群逃生开关，不进界面，也供提取机制的单测使用。
- 模块：
  - `core/group-answer-files.js`：路径、读取、核对；
  - `core/group-chat-orchestrator.js`：`registerAnswerFile` / `applyAnswerFile`，以及正文门控；
  - `main/groupchat/dispatcher.js`：派发时登记；
  - `renderer/meeting-room.js`：`_renderAnswerCard`。

## 验证

- 单测：`tests/unit-group-answer-files.test.js`。
- 真实派发器 + 可控 Claude 夹具的界面测试：`tests/e2e-group-answer-files-cdp.js`，覆盖文件优先于聊天、还没交、补救、Hub 关闭期间更新、下一轮上下文。
- 不代表真实模型会稳定写文件。模型忘了写时卡片显示「还没交」，由用户进会话处理。
