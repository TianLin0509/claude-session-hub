# AI 编排：自然语言驱动的星型协作（2026-10-22）

## 负责人模式（2026-10-23 用户决定，覆盖下文同类规则）

- 编排员改称「负责人」，定位是懂技术的项目负责人，不是纯调度：亲自理解需求、定方案与接口、结合成员特点分工、审查成员摘要；有疑点时让成员复核、亲自读关键代码或跑检查核实，或请另一位成员交叉复核。细节实现、批量改代码、跑测试、读长日志交给成员。结项前至少亲自核实一处关键证据，并以 `orch_report(kind=final)` 结项。
- 用户只和负责人对话。负责人群里成员回答卡片默认折叠成一行（显示结论），点开看全文；负责人卡片照常展开；侧栏仍可随时打开成员会话。2026-10-06「新回答默认展开」误丢了这条默认，已恢复，仅作用于负责人群。
- 负责人→成员：`orch_send_message(to,message,interrupt)`。对方空闲立即开始；对方工作中默认排队，`interrupt=true` 走与群聊插话相同的闭环提交，把指示追加进当前回合。确定没写进去（notSent）退回排队；写进去但无回执记为「可能已送达」，不自动重发。
- 成员→负责人：消息并入 Hub 通知，不再单独开一轮。`wake=true`（默认）叫醒负责人，限于卡住需拍板、发现与方案冲突的事实、完成里程碑；`wake=false` 只留言，随下次唤醒送达。成员交流抄送同样不单独叫醒。几乎同时到达的唤醒在 8 秒窗口内合并成一次。
- 成员交付时，通知直接附回答开头的摘要（约 1200 字，成员按「结论 / 改了什么 / 怎么验证 / 哪里不确定 / 需负责人决定」写）。`orch_status` 只带最近 10 条通信和未结消息，文本截到 300 字；不再要求每次唤醒先查状态。
- `orch_allow_peer(memberA,memberB,allow,reason)`：负责人主动开放或收回两位成员的直接交流，用于辩论、开发与审核对接等；原有申请审批保留。
- 项目档案：按工作目录一份，存 Hub 数据目录 `orchestration/project-briefs/`（不写进项目仓库），负责人接任务先读、结项时更新，成员只读。该目录与 transcripts 一样加入 Claude `--add-dir`，读取免审批。
- 验证：`tests/e2e-lead-mode-live.js` 用真实 Claude（负责人）、Codex、DeepSeek 跑「修 bug + 中途追加要求 + 独立审查」，在 Hub 外独立运行项目测试核对结果，并统计负责人唤醒次数。

## 当前行为（2026-10-22 用户决定，覆盖下文历史规则）

- 编排员可以选择群聊支持的任意 AI 和模型，通常兼任方案规划者。用户决定选型；Hub 不设编排员模型白名单。
- 用户用自然语言说明目标、分工、时间和停止条件。取消编排层的轮数、总时长、连续空唤醒、重复故障次数上限；暂停与结束入口仍保留。故障与交付证据继续可见。
- 编排员与所有成员可双向交流。`orch_send_message(to,message)` 在收件人空闲后送达；各收件人独立排队，成员工作期间可以向负责人提问。
- 普通成员互聊先 `orch_request_peer(memberId,reason)`，编排员用 `orch_decide_peer(requestId,approve,reason)` 决定。批准后双方可互发消息并抄送编排员；新任务清除旧授权。
- `orch_propose_plan` 仅 summary 必填，固定工作段可选。自由协作完成后可以汇报结项；有未完成的通信/单独提问时不可假结项。选择固定工作流时仍核对其交付证据。
- Claude/Codex/CodeAgent 保留原生 MCP；所有模型都可用群规提供的本机命令及 UTF-8 JSON 参数文件调用同一工具。服务端按每会话凭据绑定身份，忽略请求正文和请求头中的冒名身份。
- 旧编排群下次使用时迁移为星型，补送规则与通信入口。既有历史回答不会批量重发；新正式回答及修订通知编排员。重启时送达不确定的消息明确标错，避免盲目重复发。
- 用户暂停后，尚未提交的通信留在队列，恢复后继续；已提交给模型的任务保留真实状态。

## 历史设计（2026-10-06，仅解释迁移来源）

## 目标

田哥在编排群里只和编排员对话，像和普通 Agent 对话一样；编排员替他排一场群聊，田哥旁观。哪里需要停下来问田哥，由编排员判断；不需要就一路推进到结项。

## 之前的问题

- 计划须经界面按钮确认，改计划（比如跳过故障成员）要再点一次。
- 运行故障一律锁死，只认「继续」「确认」这类整句短词才解除；「deepseek有故障，后续跳过他就行，其他人继续」「你直接继续」都不算，编排员只能反复请田哥去界面点按钮。

## 现在的规则

| 事项 | 做法 |
|---|---|
| 计划 | `orch_propose_plan` 提交即生效，改计划同样直接生效；派工仍须匹配当前计划的工作段 |
| 田哥回话 | 对编排员说任何话都解除暂停（额度用满除外），这句话怎么理解、下一步做什么由编排员判断；@成员 不解除 |
| 运行故障 | 不再锁死，Hub 把失败步骤和可用手段告诉编排员：`remind`、`orch_restart_member` + `continue`、`skip`、`cancel` 后改计划；工作段启动失败同样交给编排员 |
| 反复故障 | 同一步骤累计 4 次运行故障（续跑后立刻再失败也算），或同一计划段启动失败 4 次，Hub 暂停（`repeated_failure`），编排员向田哥说明；田哥回话后解除，计数清零 |
| 额度 | 仍是硬上限。用满时编排员在对话里问，田哥同意后编排员调 `orch_grant_budget`：`sourceQuote` 必须出自田哥在额度用满之后发的消息，每条消息只能用一次；追加额度只解除额度暂停，不解除田哥的暂停或等他回话的暂停。田哥直接说了新上限时，编排员按新额度改计划，额度够了随计划恢复 |
| 跳过与报错可见 | 跳过记录写明是编排员还是田哥跳过、原因（`orch_control_workflow(skip)` 的 `note`），写进下一位成员的提示和群聊系统提示；成员调用模型报错时，回答卡片显示报错摘要与原文，工作流暂停原因也带上成员名和报错原文 |
| 结项 | 不变：全部计划段有审核或收口证据才能 `final` |
| 界面 | 去掉确认、恢复、追加额度按钮；状态条只留计划账本、暂停、结束编排（结束后可恢复编排） |

## 兼容

- 旧账本里「计划待确认」的计划在加载时直接生效，`settings.requireConfirm` 删除。
- 编排员守则随群规则一起发送；群规则指纹变化时，下一次派发会自动重发一次（`core/group-chat-orchestrator.js` 的 `buildFirstDelta`，旧回执无指纹也会补发）。所以旧编排群在下一条消息就拿到新守则。（2026-10-07 更正：此前写的「旧群仍带旧守则」不成立。）
