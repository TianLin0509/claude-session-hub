一、现象与用户期望

用户描述：「目前用户输入信息后，要经过较长时间的处理，信息才会被输入到 shell 界面。我理解信息可能会经过一些简单的处理来识别是 debate 模式还是什么模式，但是我认为这最多只需要 0.5 秒，不应该像现在这样，时延这么高。」

期望目标：从「回车」到「文本出现在 Claude / Gemini / Codex 三个 PTY 面板」的总耗时 < 1 秒。

理论可行性：命令解析（debate / summary / 私聊路由）+ Prompt 拼装本就是字符串操作，应在 10-20ms 内完成；剩余预算（> 900ms）足够覆盖 IPC 往返 + PTY 写入。当前 ~8 秒属于实现层面的过度保守，并非协议或硬件限制。

瀑布图核心结论

三家 AI 通过 Promise.all 并行 fanout，但每家函数体内部有串行 sleep。结果：总延迟 = max(Claude_8s, Gemini_8s, Codex_5s) + write_delay ≈ ~8.5 秒。

即使三家都已 ready 且 markers 已出现，地板仍是 8 秒，无任何方式可在当前实现下做到 1 秒以内。

四、根因分解

4.1 关键代码片段（含注释原文）

// main.js:533-559
async function _rtSendToPty(sid, prompt, kind) {
  if (kind === 'claude') {
    // Claude TUI 用 alt-screen，buffer 抓取不可靠 → fire-and-forget 8s 初始化
    await new Promise(r => setTimeout(r, 8000));   // ★★★ 主因 A
  } else if (kind === 'gemini') {
    const ready = await _rtWaitCliReady(sid, kind, 60000);
    if (!ready) return false;
    // Gemini markers 出现快但 OAuth/auth init 慢 → markers 后再等 8s 稳定期
    await new Promise(r => setTimeout(r, 8000));   // ★★★ 主因 B
  } else if (kind === 'codex') {
    const ready = await _rtWaitCliReady(sid, kind, 60000);
    if (!ready) return false;
    // Codex 启动 init phase 也需缓冲（含 MCP server spawn）
    await new Promise(r => setTimeout(r, 5000));   // ★★★ 主因 C
  }
  sessionManager.writeToSession(sid, prompt);
  const baseDelay = kind === 'codex' ? 500 : 250;
  const sizeDelay = Math.min(Math.floor(prompt.length / 100) * 10, 500);
  await new Promise(r => setTimeout(r, baseDelay + sizeDelay));  // ★ 次因 D
  sessionManager.writeToSession(sid, '\r');
}

关键洞察：A/B/C 是「冷启动税」被错误地每轮重收

从注释可以看出，这三条 sleep 设计的初衷是覆盖 CLI 进程启动期的初始化（TUI alt-screen 切换 / OAuth 认证 / MCP server spawn）。但这些初始化是持久且不可逆的——CLI 一旦完成首次启动并响应了第一个 prompt，就不会再「未初始化」。第 2/3/4 轮的 sleep 是纯纯白白等的，没有任何技术依据。

六、私聊 vs 圆桌的关键对比

同一份代码里，私聊路径（@claude / @gemini / @codex）跑得很快，圆桌却慢 8 秒。这是最直接的反证——圆桌的保守设计是冗余的。

维度 私聊路径 圆桌 fanout 路径
入口 renderer/meeting-room.js 私聊分支（约 1367-1403） main.js:_rtSendToPty
IPC 路径 renderer 直接 ipcRenderer.send('terminal-input', ...) renderer → 'roundtable:turn' → main.js → orchestrator
CLI ready 等待 无 _rtWaitCliReady（最长 60s）
固定 sleep 无（仅 200/400ms 后发回车） Claude 8s / Gemini 8s / Codex 5s
体感延迟 < 500 ms ~ 8 s
这意味着什么

用户已经在使用私聊路径，证明 PTY 写入本身从来没有任何"PTY 缓冲吞回车"问题。圆桌之所以加这堆 sleep，唯一合理的初始动机就是「圆桌可能在 session 刚创建毫秒级就 fanout，而私聊由用户手动点入面板，CLI 已 ready」。即首次发送的冷启动等待。结论：保留首次的 ready 等待，后续全部走私聊那种短路径。

七、优化方案

现状

~ 8500 ms
  • 每轮三家固定 sleep 5-8s（Promise.all 并行但内部串行）
  • 写完 prompt 后 250-1000ms 才发回车
  • _rtWaitCliReady 每轮重 poll，间隔 300ms
  • orchestrator state.json 同步写盘

P0 改造后（热路径）

< 200 ms
  • session 级 ready 缓存：首次 ready 后直接走快路径
  • 一次性 write(prompt + '\r')，无中间 delay
  • 活性兜底：写完 300ms 内若无任何 PTY echo → 重置 ready 走冷启动
  • orchestrator state.json 异步写（不阻塞 fanout）

7.1 P0 — 三方共识的最小改造

P0-1 · 引入 sessionRoundtableReady 缓存

P0

SessionManager 维护 per-sid 的 roundtableReady: boolean。首次 _rtWaitCliReady 通过后置为 true。后续 _rtSendToPty 看到 ready=true 直接进入快路径。

  • 修改：core/session-manager.js — 给 session 增字段
  • 修改：main.js:533-559 — _rtSendToPty 分快慢路径
  • 预期收益：第 2 轮起 8s → 0ms（节省主因 A/B/C）

P0-2 · 删除 prompt → '\r' 中间 delay

P0

两次 writeToSession 合并为一次：write(prompt + '\r')。删除 baseDelay + sizeDelay。

  • 修改：main.js:554-558
  • 预期收益：每轮节省 250-1000ms（次因 D）
  • 顾虑：「PTY 缓冲分块吞回车」是物理串口时代的过虑——node-pty + 现代 OS 的 PTY 缓冲远超 prompt 大小

P0-3 · 活性兜底（替代固定 sleep 的安全网）

P0

fast path 写完 prompt 后，启动 300ms 计时；若期间 PTY 无任何新 byte，则视为 session 失活，重置 ready=false 并立即走冷启动，再发一次。

  • 新增：activity 监听（onBufferUpdate → markActivity）
  • 覆盖场景：用户后台 Ctrl+C kill CLI、CLI 自己 crash、PTY 异常
  • 预期：99% 走 fast path（< 200ms），1% 极端情况花和现在差不多

P0-4 · _rtWaitCliReady 仅冷启动用

P0

当前每轮都 _rtWaitCliReady → 改成只有 sessionReady === false 时才调。轮询间隔从 300ms 改 100ms（冷启动更快确认 ready）。

  • 修改：main.js:520-531
  • 预期：冷启动也加速 ~200ms

7.2 P0 完整伪代码（DeepSeek 给出，已校对）

// 模块级状态
const sessionRtState = new Map(); // sid → { ready: boolean, lastActivity: number }

// 在 PTY 数据监听中调用：每次 PTY 有新输出就更新 lastActivity
sessionManager.on('buffer-update', (sid) => {
  const st = sessionRtState.get(sid);
  if (st) st.lastActivity = Date.now();
});

async function _rtSendToPty(sid, prompt, kind) {
  let st = sessionRtState.get(sid);
  if (!st) { st = { ready: false, lastActivity: 0 }; sessionRtState.set(sid, st); }

  // === 1. 冷启动：仅首次或 ready 重置后 ===
  if (!st.ready) {
    const ok = await _rtWaitCliReady(sid, kind, 60000);  // 仅 marker 轮询，无 8s sleep
    if (!ok) return false;
    st.ready = true;
    st.lastActivity = Date.now();
  }

  // === 2. 热路径：一次性 write，无中间 delay ===
  sessionManager.writeToSession(sid, prompt + '\r');

  // === 3. 活性兜底（300ms 内无 echo → 走冷启动重试一次）===
  const before = st.lastActivity;
  await new Promise(r => setTimeout(r, 300));
  if (sessionRtState.get(sid).lastActivity === before) {
    st.ready = false;
    const ok = await _rtWaitCliReady(sid, kind, 60000);
    if (!ok) return false;
    st.ready = true;
    sessionManager.writeToSession(sid, prompt + '\r');
  }
  return true;
}

async function _rtWaitCliReady(sid, kind, maxMs = 60000) {
  const need = _RT_READY_MARKERS[kind] || [];
  const start = Date.now();
  const pollMs = 100;  // 从 300ms 改 100ms
  while (Date.now() - start < maxMs) {
    const buf = sessionManager.getSessionBuffer(sid) || '';
    if (need.length === 0) { if (buf.length >= 1500) return true; }
    else if (need.some(m => buf.includes(m))) return true;
    await new Promise(r => setTimeout(r, pollMs));
  }
  return false;
}

八、风险与活性兜底设计

风险场景是否被现有缓存方案覆盖兜底机制
用户在 turn 间手动 Ctrl+C kill 了 CLI 是 ✓ 活性兜底：write 后 300ms 无 echo → 重置 ready 走冷启动
CLI 自己 crash（OOM / panic） 是 ✓ 同上 + PTY 进程退出会触发 session-manager 通知
PTY 异常断开但进程仍活 是 ✓ 同上（无 echo）+ 已规划在容错升级方案中加 transport_lost 状态
Gemini OAuth token 过期需要重认证 部分 会出现 prompt 但无后续输出 — 不在本次改造范围；走 turn-complete watchdog（容错方案的 soft alert）
Codex MCP server 二次启动 部分 极少出现（只有显式 reload）；如出现则活性兜底重置 ready 重新等
为什么 300ms 活性窗口足够安全

node-pty 在主流平台上的 echo（用户输入立即由 PTY slave 回显）通常 < 10ms。即使是 TUI 程序在 alt-screen 下，CLI 收到字符到产生任意新输出（可能是光标重画、状态栏更新）也基本在 50ms 内。300ms 给了 6× 余量。

即便 300ms 偶尔误判，也只是多走一次冷启动，不会丢消息或导致错误回答。
