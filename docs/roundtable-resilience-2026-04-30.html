一、现象与根因

1.1 现象

通用圆桌（Roundtable）第 1 轮触发后：

  • Claude 已回答（角标「已答 ✓」）
  • Codex 已回答（角标「已答 ✓」）
  • Gemini 终端面板里能看到完整文本「下午好！很高兴加入今天的圆桌讨论…」，输入框已回到 Type your message or @path/to/file
  • 但 UI 上 Gemini 卡片始终显示「思考中」+ 进度条动画
  • @debate / @summary / 群策群力 全部 disabled，10 分钟内无法推进

根因（一句话）

Gemini 完成检测的唯一触发条件是 JSONL 行携带 tokens.total != null 字段（core/transcript-tap.js:568-570）。该字段在慢响应、限流降级、多 turn 工具调用等场景下可能滞后或永不写入，导致 turn-complete 事件不发；而 watchdog 设置为 600000ms（10 min）（core/roundtable-orchestrator.js:21），这 10 分钟内 Promise.all（main.js:676-684）始终 pending，orchestrator 不退出 inProgress，所有推进按钮 disabled（renderer/meeting-room.js:1243）。

1.3 三家 AI 完成信号横向对比

CLI 触发机制 语义层级 可靠性 代码位置

Gemini session JSONL 行携带 tokens.total != null 启发式字段（实现细节，非协议契约） ★★ transcript-tap.js:568-570
重要发现：Gemini CLI 有官方完成信号

Gemini CLI Headless 模式（--output-format stream-json）的 JSONL 事件流定义了 type:"result" 事件，是文档化的「final outcome」标记，等价于 Codex 的 task_complete 和 Claude 的 hook。当前 Hub 没用上是因为 spawn 方式不是 headless。详见 参考文献。

二、三层完成信号模型

核心设计原则：语义事件 (L1) > 传输完成 (L2) > 启发式 (L3)。L3 永远只做软提醒，不做强制终结。

为什么 L3 永不强制终结

用户质疑过：基于「N 秒空闲」的判定会误杀正常工作的 AI（典型场景：Gemini 调用 web search 工具 5s、深度推理 token 间隔拉长）。结论：任何沉默推断都不能作为终结信号。L3 仅用于在 UI 上闪一个非阻塞提醒条，让用户决定是否手动介入；不点就一直等下去（直到 L1/L2 自然触发）。

2.1 Gemini L1 接入策略

当前 Hub spawn Gemini 的方式是 TUI 全屏交互模式（你截图能看到彩色 banner、提示符）。要拿到 type:"result" 事件，有两条路径：

方案 侵入性 用户体验影响 评级
A. 圆桌模式下改用 headless --output-format stream-json 中（要改 Gemini 启动参数 + 输出渲染） 失去 Gemini TUI 彩色界面，但圆桌不需要 ★★★★★ 推荐
B. 监听 TUI 模式下 JSONL 的 message_update 终结行（v0.40+ 新增） 低（仅修改 transcript-tap.js） 无 ★★★★ P0 fallback
C. 接入 Gemini CLI 的 --acp 协议（JSON-RPC over stdio） 高（重写 spawn + 通信层） 无 ★★★ P3 长线

P0 实施 A + B 双路：圆桌专属 spawner 用 headless，但 transcript-tap.js 也升级支持 type:"result" 和 message_update 行检测，TUI 模式也能跟着受益。

三、状态机重构

从现行 4 态扩展为 8 态，覆盖所有可能的 AI 生命周期。

五、实施分期 P0~P3

P0 · 根因修复 + 用户逃生

P0

解决卡死，让用户有逃生通道。预计 2-3 天。

  • Gemini 检测加入 type:"result" 行识别（最强信号）
  • Gemini 检测加入 message_update 终结行识别（v0.40+）
  • watchdog 600s → 软提醒 90s/180s（不强制终结）
  • Promise.all → Promise.allSettled，inProgress 不被单家阻塞
  • 新增 IPC：roundtable-manual-extract、roundtable-skip-participant、roundtable-resend
  • UI：每个 AI 卡片底部「逃生工具栏」（手动提取/查看 transcript/跳过/重发）
  • UI：圆桌主区域「软提醒 banner」（90s 触发，可关闭）
  • 状态机扩展：manual_extracted / absent / soft_alert 三态

P1 · 状态机重构 + L2 信号补充

P1

把临时状态机重构为 8 态完整模型。预计 1-2 天。

  • 统一 ParticipantState：8 态枚举，明确转移条件
  • L2 信号：监听 PTY 进程退出事件，区分正常退出 vs 异常退出
  • errored / interrupted / transport_lost 三态独立 UI
  • 历史轮次面板显示每家在每轮的最终状态（含手动/缺席角标）

P2 · Codex 多 turn 加固

P2

现行 task_complete 在多 turn agent loop 时可能误报。预计 1 天。

  • task_complete 触发后再等 N 秒（建议 3s），观察是否有新 turn 起始事件
  • 有新 turn → 取消本次 turn-complete，继续等下一个 task_complete
  • 无新 turn → 确认完成，emit turn-complete
  • 边界：Codex 显式 task_complete + last_agent_message:null 判定为 errored 而非 completed（issue #13769）

P3 · 协议级 IPC（长线）

P3

从文件 tail 升级为 JSON-RPC 长连接。预计 5-7 天。

  • Gemini：接入 --acp 模式，JSON-RPC over stdio
  • Codex：接入 codex app-server，stdio / unix socket / websocket 三选一
  • Claude：保持现有 hook（已是协议级）
  • 统一抽象 ProviderTransport 接口，文件 tail 作为兼容老版本的 fallback

六、风险与回退

风险 影响面 缓解 回退
Gemini headless stream-json 不支持当前 spawn 用的某些参数 P0 Gemini L1 接入失败 P0 用 fallback B（TUI + message_update）兜底；分两批 PR 仅保留 fallback B，不强行接入 stream-json
