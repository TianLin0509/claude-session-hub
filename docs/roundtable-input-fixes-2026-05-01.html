② Bug B：「创建中」状态永久卡死（不点对话不切换）

项当前现象修复后
表现 三个 AI 卡片永久显示「创建中…」，即使 PTY shell 已经完全启动并显示 prompt — 除非用户实际问出第一个问题、AI 答完一题，才会切到下一状态 CLI 启动完毕（buffer 含 ready marker 或 ≥1500 字符），UI 立即切到「待命」
根因 _renderFusedTabs:165 的 isInitializing 判断错用了 markerStatus。
但 markerStatus（summary-engine.js:79）是检测 "summary marker（特殊标记符号 START_MARKER..END_MARKER）是否产出过"，session 刚 ready 但没回答过问题时永远是 'none' → isInitializing = true → 永久卡死。
markerStatus 的语义根本不是"session 是否就绪"。 		方案 A：新增 IPC cli-ready-status(sessionId)
复用 main.js:564 _RT_READY_MARKERS 已有的 ready 判断逻辑（gemini='Type your message'/codex='gpt-5.X'/claude=buffer≥1500 字符）。renderer 改用此 IPC 而非 markerStatus 判断 isInitializing。

真正的 CLI ready 信号（已存在但未被 UI 用到）

kind就绪信号（来自 main.js:564 _RT_READY_MARKERS）
claudebuffer 长度 ≥ 1500 字符（启动屏 + 提示符 ANSI box 通常 ≥2KB）
geminibuffer 含 'Type your message' / 'YOLO' / 'gemini-' 任一
codexbuffer 含 'gpt-5.5' / 'gpt-5.4' / 'Context 100%' / 'send' 任一

这套逻辑已在 _rtWaitCliReady（异步轮询版本）使用，本次只是把同样判断暴露为同步 IPC 给 UI 用。

main.js 新增 IPC handler（复用 _RT_READY_MARKERS）： 
ipcMain.handle('cli-ready-status', (_e, sessionId) => {
  const session = sessionManager.getSession(sessionId);
  if (!session) return false;
  const kind = session.kind;
  const buf = sessionManager.getSessionBuffer(sessionId) || '';
  const need = _RT_READY_MARKERS[kind] || [];
  if (need.length === 0) return buf.length >= 1500;   // claude / glm 走长度兜底
  return need.some(m => buf.includes(m));              // gemini / codex 走文本匹配
});
renderer 替换 isInitializing 判断（meeting-room.js:165）： 
// 旧（错的）：
// const isInitializing = s && markerState !== 'done' && markerState !== 'streaming';

// 新（正确）：
const isInitializing = s && !_cliReadyCache[sub.sid];
renderer 新增 cli-ready 轮询（与 markerPoll 并存，独立 timer）： 
let _cliReadyCache = {};   // sid → boolean，ready 后不再变 false（直到 closeMeetingPanel）
let _cliReadyPollTimer = null;

function startCliReadyPoll() {
  if (_cliReadyPollTimer) return;
  const pollOnce = async () => {
    if (!activeMeetingId) return;
    const meeting = meetingData[activeMeetingId];
    if (!meeting) return;
    let changed = false;
    for (const sid of meeting.subSessions) {
      if (_cliReadyCache[sid]) continue;   // 已 ready 的不再 poll
      const ready = await ipcRenderer.invoke('cli-ready-status', sid);
      if (ready) { _cliReadyCache[sid] = true; changed = true; }
    }
    if (changed) {
      renderTerminals(meeting);  // 触发卡片重新渲染（让 isInitializing 切换）
      _refreshSoftAlert();        // 触发 banner 更新
    }
    // 全部 ready 后停止轮询
    if (meeting.subSessions.every(sid => _cliReadyCache[sid])) {
      stopCliReadyPoll();
    }
  };
  pollOnce();   // 立即触发一次（不等 1s）
  _cliReadyPollTimer = setInterval(pollOnce, 1000);
}

function stopCliReadyPoll() {
  if (_cliReadyPollTimer) { clearInterval(_cliReadyPollTimer); _cliReadyPollTimer = null; }
}

⑥ 风险与边界

场景处理
用户在 banner 出现前已经在输入banner 出现不会清空 input（仅显示在上方），不影响用户体验
banner dismiss 后再次进入会议室每次 openMeeting 重置 _bannerDismissed = false，banner 再次正常显示
无 sub 会话时 banner不显示（subs 数组空时 isInitializing 计数 = 0）
auto-focus 影响用户先看终端的需求仅在 openMeeting 首次时 focus；用户点终端后 focus 切走，不会反复抢回
cli-ready-status IPC 轮询开销仅查 ring buffer + indexOf，O(N) 字符串扫描；ready 后停止轮询。3 个 sub × ≤1 次/s × 至多 ~30 次（ready 前） ≈ 90 次 IPC/会议室，开销可忽略
cliReady 误判（buffer 含 ready marker 但 CLI 实际还没准备好）ready marker 是 CLI 启动屏关键文本（gpt-5.X、Type your message 等），出现即代表 prompt 可见，对用户而言已经"看上去 ready"。极端情况下输入会被 CLI 缓冲，不影响功能
