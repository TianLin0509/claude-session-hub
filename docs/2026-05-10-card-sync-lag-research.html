卡片视图相对 PTY 同步滞后 · 调研报告

2026-05-10 · Claude Session Hub · 立花道雪 / Claude Opus 4.7 联合调研
结论先行 · 卡片同步显著滞后是真问题，但根因不是渲染没优化好——是 PTY 与 JSONL transcript 是两条本质不同节奏的数据通路。PTY 流 token 字节（实时），JSONL 在 LLM-call 边界整行写盘 （节拍 1-50s 不等）。即使 Hub 已经做了 250ms throttle + 增量 mount + parser yield，仍受限于上游 JSONL 写盘 节奏。要追上 PTY 必须改链路，不是再调参数。

1.2 卡片视图链路 事件驱动 + 节流

claude.exe LLM call 完成（不是 token 完成！） ↓ Claude CLI 把整条 message entry append 到 JSONL ~/.claude/projects/<proj>/<sid>.jsonl 触发器有 3 条： A. 2 · 滞后源 5 项（按贡献度排序）

① 最大 JSONL 是 LLM-call 边界写，不是 token 流式写

Claude CLI 在每次 LLM call 完成时把整条 entry append 到 JSONL，不会按 token 增量 flush。PTY 看到的 streaming token 不会反映到 JSONL，直到本次 LLM call 完成。

实测样本：抓取一个真实 transcript（57c416cd-d292-463b-a2bb-e1b0fd5ec2e9.jsonl，195 KB）：

指标值
总 entries50
assistant entries23
stop_reason='tool_use'（中间步）22
stop_reason='end_turn'（一轮真完成）1
inter-entry interval p50 / p90 / p99 / max486ms / 7.9s / 49.7s / 49.7s
间隔 > 5s 的 multi-step gaps7

→ 单 user prompt 触发 22 次 tool_use entries + 1 次 end_turn。merge 把它们聚合成 1 个 logical turn。 但每 entry 在 PTY 上耗时不同，p99 间隔 49.7 秒，意味着用户在 PTY 上看到了 token 流，但 JSONL 写盘要等 LLM call 收完整轮。

code refs · core/claude-transcript-parser.js:153-217 _mergeConsecutiveAssistantTurns； renderer/renderer.js:4184-4187 turn-complete 触发条件注释

② 关键 250ms throttle 在 PTY 字节静默后不会再触发

renderer.js:4190-4214 的 throttle 是 leading-edge：第一字节 schedule 一次，后续字节落同窗口不再 schedule， 最后一字节后已 schedule 的 timer fire 跑最后一次 reload。

但那一次 reload 时 JSONL end_turn entry 可能还没写盘——PTY 字节静默 ≠ Claude CLI 已 commit JSONL （CLI 异步 fsync，节奏受 LLM call 完成、Stop hook 调度、Node fs.append flush 多重影响）。reload 拿到的还是上一次 tool_use 状态，卡片定格 → 用户看到 PTY "答完了" 但卡片没同步。

之后 PTY 不再有字节 → throttle 不再触发 → 卡片必须靠 turn-complete-event（路径 B）兜底。

③ 中 路径 B 兜底链路最长 15 秒

Stop hook 正常触发：<50ms（main.js HTTP /api/hook/stop → notifyStop → emit）。但实际链有多档兜底：

  • _CLAUDE_STOP_REASON_DEBOUNCE_MS = 200：JsonlTail 见到终态 stop_reason 后 200ms 防抖窗口
  • _CLAUDE_IDLE_EMIT_MS = 15 * 1000：transcript 写入异常 / Stop hook 没触发时的最终兜底

正常情况 Stop hook 应能拦在 50ms 内。异常情况（Stop hook 被吞 / settings 没部署 / 圆桌切上下文）卡片 要等 15s。这就是用户偶发感知"卡片同步很慢"。

code refs · core/transcript-tap.js:142,149

④ 中 parser 长 transcript 主线程阻塞 218ms

每次 throttle reload → IPC parse-session-transcript → main.js setImmediate yield + fs.readFileSync 全文件 + JSON.parse per line + merge。

main.js:2353-2356 注释：5MB transcript ~218ms 主线程阻塞；core/parser.js:223 注释：5MB readFileSync 仅 9ms。差异在 JSON.parse + merge 那段。长会话（>1MB）每 250ms 触发一次解析，主线程负担重。这不是直接的"滞后"， 但在阻塞间隙里 turn-complete-event / hook IPC 也会延迟到达，间接放大其它路径的滞后。

⑤ 小 JSONL fs.appendFile 在 Windows NTFS 的 writeback 延迟

Claude CLI 用 Node.js fs.appendFile 写 transcript。Windows NTFS 默认 writeback cache，append 后内容在 内存缓冲，readFileSync 通常能读到（同进程不必）。但 Hub 在 main process（Electron），Claude CLI 在 PTY child process — 跨进程 readFileSync 走 OS 文件系统层，受 NTFS 元数据 / change journal 影响，偶发 50-200ms 读不到最新 append 行（社区已知 Windows fs.watch / fs.read 延迟问题）。

实测影响小，但与 ② 叠加放大"最后一次 reload 错过 end_turn 行"概率。

3 · 改进方案（4 档）

P0立等可见 · stream-end fallback timer

问题对应：滞后源 ② —— 250ms throttle 错过最后一次写盘。

方案：在 renderer.js:4163 terminal-data handler 内，除 250ms throttle 外，再叠一层 "PTY 静默 800ms 后 final reload"：

// 已有的 250ms throttle 保留不动
// 追加：每个 chunk 重置 _stopTimer，800ms 静默后跑一次 final incremental reload
clearTimeout(_stopTimerBySid.get(sessionId));
_stopTimerBySid.set(sessionId, setTimeout(() => {
  if (sessionId === activeSessionId && currentView === 'card') {
    loadSessionHistoryToOverlay(sessionId, { incremental: true }).catch(() => {});
  }
}, 800));

收益：覆盖 Claude CLI 写盘节奏 + Windows fs writeback 延迟。Stop hook 失效场景下，最差 800ms 内卡片追上（不再依赖 15s idle 兜底）。

代价：~10 行代码、~16 字节内存/session、单次额外 reload（短会话毫秒级，长会话受 ④ 影响）。

风险：低。

P1中等改造 · parser per-session 增量缓存

问题对应：滞后源 ④ —— 每次 reload 全文件 readFileSync + parse。

方案：main.js 维护 Map<transcriptPath, ParserCache>：

{
  mtime: number,           // 上次 stat mtime
  byteOffset: number,      // 已解析到的字节偏移
  flushedTurns: Turn[],    // 已 flush 的 logical turns（merge 完成的）
  pendingAcc: Acc | null,  // 当前累加中的 turn group（未遇 end_turn / user）
  toolResultMap: Map,      // tool_use_id → result 关联
}

每次 IPC parse-session-transcript：

  • fs.stat 拿 mtime；mtime 没变 → 直接返 [...flushedTurns, snapshotOf(pendingAcc)]（<1ms）
  • mtime 变了 → seek byteOffset 读 tail 增量 → 新 entries 累加进 pendingAcc → 遇 end_turn / user 时 push 到 flushedTurns

关键安全点：merge 不能纯 tail-only（注释明示），但可以跨调用维护 acc 状态——pendingAcc 就是"上一次没 flush 的 group 头"，新增 entries 直接 join 进去。

收益：5MB transcript 218ms → ≤5ms（仅读增量）。彻底解决 ④。

代价：~80 行代码 + cache 管理（session 关闭清理、文件 truncate / 删除检测）。

风险：中。需要测试用例覆盖 truncate / 文件被外部改写 / 多 Hub 实例并发场景。

P2架构级治本 · JsonlTail 直推 renderer，绕过 PTY-byte 触发

问题对应：滞后源 ①②③ —— 整个"PTY 字节触发 reload"模型偏移。

现状：core/transcript-tap.js:285 已有 JsonlTail 在 fs.watch JSONL 文件，onLine 拿到每行 实时。但目前只用来调度 stop_reason emit，没把"per-line 增量"推给 renderer。

方案：

  • ClaudeTap.onLine 拿到一行 entry → 立即 broadcast 'transcript-line-event' { hubSessionId, entry }
  • renderer 维护 per-session merge state（搬 _mergeConsecutiveAssistantTurns 逻辑到 renderer 或 shared module）
  • 收 entry → 累加到 acc → in-place update 卡片 （turn.id 用 acc 第一个 entry uuid，已 mounted 时 mountSessionTurnCard 触发 in-place replace）
  • 不再依赖 PTY-byte 触发的 250ms throttle reload
  • 不再每次重新解析全 transcript

收益：真正逼近 PTY 实时。每写一行 JSONL → 几 ms 内卡片更新。彻底解决 ①②③④。 卡片视图与 PTY 视图同时刻看到同样语义内容（PTY 看 token，卡片看 entry-边界 turn）。

代价：~250 行重构。merge 逻辑搬到 renderer 后，main.js parse-session-transcript 还是要保留（视图切换、 冷启动加载历史）。两条 path 的 acc 状态需要同步（或 renderer 启动时拉全量、之后增量）。

风险：高。fs.watch 在 Windows 下偶发不触发；JsonlTail 已踩过这个坑（idle timer 兜底）。 要保证 "watch 漏 + idle 兜底 + 全量 reload 三档协同"。

P3不推荐 · 直接基于 PTY 字节流增量解析

从 PTY 字节流 ANSI 解析提取 turn 文本。违反 CLAUDE.md "上游数据源"原则——下游渲染多层易翻车。已知不可行：

  • Claude TUI 用 Ink，不停整屏重绘；ANSI 状态机难维护
  • thinking / tool_use / text 在 PTY 上是混合的视觉块，没有结构化分隔
  • 已经放弃过（renderer.js:4159 注释 "Tool block folding 已废弃 2026-04-28"）

4 · 推荐路线

建议分两步走：
  1. 第一步：P0 立即上 — 8-15 行代码，800ms stream-end fallback。覆盖 90% 用户日常感知场景， 几乎零风险。可以今天就 commit。
  2. 第二步：根据 P0 落地后的反馈决定
    • 如果用户仍偶发感知滞后（长 transcript > 2MB 场景）→ 走 P1（parser 缓存），治标治本。
    • 如果想做到"卡片视图与 PTY 视觉同步性 100%"（演示场景、UX 卖点）→ 走 P2（JsonlTail 直推）。 但风险与收益要权衡——目前 stop_reason='end_turn' 后 200ms emit + Stop hook 实际 50ms emit 已经是不错的体验， 除非追求极致流畅。
