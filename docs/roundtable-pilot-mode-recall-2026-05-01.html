②历史文件统一记录现状

项目当前有 3 个独立的历史文件，分散记录：

数据文件路径格式主驾相关
圆桌每轮记录 <arena>/<meetingId>-roundtable.json JSON 数组（turns） 仅记录多人轮次，不含主驾期间
主驾私聊 <arena>/<meetingId>-roundtable-private.json JSON（按 kind 分类） 主驾期间消息进这里
自由对话 timeline <arena>/<meetingId>.json 的 _timeline JSON 数组 摘要可存这里作为系统消息
现状评估：JSON 格式对 AI 不友好（解析成本高、噪声字段多）。统一性也差（要查全貌得读 3 个文件）。
设计建议：主驾模式落地时同步生成一份 统一 markdown 镜像：<arena>/<meetingId>-pilot-recap-<timestamp>.md，专为副驾 AI 阅读优化。这本质上是把 3 个 JSON 转成 1 份对话 markdown，AI 读 1 个文件就能拿到全貌。

③6 种"按需查询"实现思路

所有思路都建立在已有 D'（主驾自动生成不限字数摘要）之上，作为"摘要不够时的兜底"。

F1 · 路径告知（你提的） 基础版

做法：主驾摘要末尾自动附 footer：

📂 完整历史: C:\Users\lintian\.claude-session-hub\arena-prompts\<meetingId>-roundtable-private.json
该文件包含本次主驾期间的全部对话（5 轮，约 1.2k 词）。
如基于摘要回答即可，则无需读取；如需细节，请用你的文件读取工具查阅。

给副驾的 prompt 完整示例：

## 你刚才暂时离场（用户和 ⚡Slot1 主驾通过 5 轮深聊）
<主驾 Claude 的不限字数摘要>

📂 完整历史: C:\...\<meetingId>-roundtable-private.json
<path 描述>

## 现在用户问大家:
那 Tesla 呢

支持矩阵：

Claude ✓ Gemini ✓ Codex ✓ DeepSeek ✓ GLM ✓ 所有 CLI AI 都有 Read / Bash 文件读取能力

优点：

  • 实现极简：prompt 末尾拼一行字符串，0 新代码
  • 所有 AI 兼容（都能读文件）
  • 用户透明：路径就是用户机器上的文件，可自己打开看

缺点：

  • JSON 格式 AI 解析成本高，可能浪费 token 在解析 schema 字段上
  • 路径暴露给 AI 心智模型有点"工程味重"
  • 大文件（如 50 轮对话）AI 读完整文件可能超 ctx

F2 · Markdown 镜像（F1 升级） 推荐基础

做法：主驾摘要生成时，Hub 同步生成一份对话历史的 markdown 镜像，给副驾的是这份 md 路径而非原 JSON。

# 主驾期会话历史 · Slot 1 (Claude / Opus 4.7)
> 2026-05-01 14:32 ~ 14:58 · 5 轮 · 1.2k 词

## 第 1 轮 (14:32)
**用户**: 如何看美股科技股
**Claude**: 当前美股科技股呈现分化...

## 第 2 轮 (14:38)
**用户**: 我重点关注 AI/半导体
**Claude**: 建议 NVDA + AVGO + AMD...

[... 后续 3 轮 ...]

给副驾的 prompt：

📂 完整历史: C:\...\<meetingId>-pilot-recap-<ts>.md
若摘要不够细，可用 Read 工具查阅这份 markdown（对话已格式化为人类可读）。

优点（相比 F1）：

  • AI 读 markdown 几乎零解析成本（按行读对话即可）
  • 用户可直接双击 md 自己看，做"对话存档"
  • 符合 Hub 的"upstream data source"哲学（CLAUDE.md 铁律）

缺点：

  • 多一次文件 IO（Hub 写 md）
  • md 与 JSON 同步失败时数据不一致风险（缓解：md 仅在切回时生成一次性快照，不维护更新）

F3 · HTTP API · 副驾用 curl 查询 中等

做法：复用 Hub 既有 hook server（main.js 监听 127.0.0.1:<port>），新增 endpoint：

GET http://127.0.0.1:<hookPort>/api/roundtable/history?meetingId=X&segment=pilot-1
→ 返回 JSON: { turns: [...], summary: "..." }

GET http://127.0.0.1:<hookPort>/api/roundtable/history?meetingId=X&segment=pilot-1&format=markdown
→ 返回 markdown 文本

给副驾的 prompt：

🌐 历史查询 API: curl "http://127.0.0.1:3457/api/roundtable/history?meetingId=<id>&segment=pilot-1"
若摘要不够细，可用 Bash 工具调用此 API 查询完整历史。

优点：

  • API 比文件更受控：可分页、按段查询、限流
  • 支持精细查询：query string 可过滤"只看第 3 轮"或"只看用户问题"
  • 未来扩展性好（语义检索 / 全文搜索）

缺点：

  • 实现成本：需新增 API endpoint + URL 设计 + 认证（避免任意进程读取）
  • port 不稳定（Hub 起多实例时 fallback 端口）需要 prompt 时动态注入
  • 所有 AI 都能 curl 但额外 1 步 Bash 调用，比直接 Read 稍重

F4 · "@hub recall"协议 · AI 在输出中嵌入查询关键词 不推荐

做法：教副驾 AI："如需详细历史，请在你的回答中先输出一行 @hub:recall pilot-segment-1，Hub 会立即把对应内容注入下一轮，你再继续回答。"

优点：

  • AI 不需要任何外部工具能力
  • 对话流自然

缺点：

  • 需要 Hub 实时解析 AI 输出 + 中断 PTY + 注入 + 续接，turn 状态机大改
  • turn-complete 检测复杂化（既有 marker 机制要适配）
  • AI 是否听话不可控（prompt 约束级别）
  • 调试困难

结论：技术风险高，违反"轻量简单"。

F5 · 索引化按需查询（F1+F2 升级） 推荐进阶

做法：摘要末尾不只给路径，而是给段落目录，让 AI 选择性读取部分内容。

📂 完整历史: <path>.md (5 段)
   段落 1 [行 1-32]   讨论 AI/半导体板块整体
   段落 2 [行 33-78]  深入 AMD 估值（PE 28x vs 历史 25x）
   段落 3 [行 79-110] NVDA 风险评估
   段落 4 [行 111-145] AVGO 与博通收购影响
   段落 5 [行 146-180] 仓位建议

如需细节，可只读对应段落（如用 Read tool 的 offset/limit 读 33-78 行）。

段落自动切分：让主驾在生成摘要时，同时输出段落目录（一次 LLM 调用产出两个东西）。

优点：

  • token 节约：AI 只读自己关心的段落，不读全文
  • 意图明确：副驾能精准定位"我需要了解 AMD 估值这块"
  • 实现可叠加在 F2 之上（multi-step 输出）

缺点：

  • 主驾 prompt 复杂化：要求同时输出摘要+段落目录
  • 段落切分质量依赖主驾

F6 · 用户主动追加 · UI 按钮 推荐高级补充

做法：Hub UI 在副驾卡片上提供一个 [📜 喂完整历史] 按钮。用户点击后，Hub 把完整 markdown 历史强制注入该 AI 的下一轮 prompt（绕过 AI 自主判断）。

触发场景：

  • 用户看到副驾 AI 第一次答得很笼统，知道它没读历史 → 点按钮强制喂
  • "完整复盘"心理需求：用户想确保所有 AI 看到全部细节

UI 示意：

┌─ Slot 2 · 🔥小火龙 ────────────┐
│ 🔥 Gemini  · 已答 ✓             │
│ 2.5 Flash · Ctx 5%              │
│ ⏱ 12s · 累计 37s · 🪙 1.2k    │
│ ─────────────────────────────── │
│ 关于 Tesla, 我看法是...          │
│ ...                              │
│ [📜 喂完整历史] [💬 私聊] ...   │
└──────────────────────────────────┘

优点：

  • 用户主权：当用户不信任 AI 自主判断时，可强制干预
  • 互补 F1/F2/F5 的不足（如 AI 错判"不需要查"导致回答粗糙）

缺点：

  • 需新增 UI 按钮 + IPC + prompt 注入逻辑
  • 用户需要"看出 AI 答得粗糙"这种判断力

⑤推荐组合：D' + F2 + F5（默认） + F6（高级）

组合方案 · 三层递进 最终推荐

第 1 层（默认始终启用）· D' 主驾不限字数摘要

切回时主驾自己生成摘要，不限字数。摘要进 timeline 用户可见。

第 2 层（默认始终启用）· F2 + F5 索引化 markdown 镜像

同时生成 markdown 镜像 + 段落目录，路径附在副驾 prompt 末尾。副驾 AI 自主判断"摘要够不够"，不够则用 Read 工具读对应段落。

第 3 层（高级模式）· F6 用户主动按钮

副驾卡片上 [📜 喂完整历史] 按钮，用户点击强制注入完整 markdown。当 AI 自主判断不准时手动救场。

三层递进的逻辑

场景触发哪一层用户感知
简单后续问题（如"那 Tesla 呢"）L1 摘要够用无感切回，副驾基于摘要回答
需要细节的问题（如"主驾刚才说 AMD PE 是多少？"）L2 副驾自主读 md 段落 2副驾回答里有具体数字，准确
用户需完整复盘（如要导出报告）L3 用户点 [📜 喂完整历史]副驾下一轮看到全部对话
主驾摘要质量差（极端）L3 用户兜底用户察觉后手动救场

为什么这样组合最优

  • 覆盖 80% 场景的 L1+L2 实现成本最低（一次文件 IO + prompt 末尾拼字符串）
  • L3 是兜底（不依赖 AI 智能判断），但只有需要时才用
  • token 经济性：L1 仅 100-300 字，L2 仅当 AI 判断需要时读，L3 仅用户触发
  • 5 家 AI 全兼容：F2/F5 都依赖 Read 工具，所有 CLI 都有；F6 是 UI 强制注入，不依赖 AI 能力
  • 用户主权：自动模式 + 手动救场，两手都有
