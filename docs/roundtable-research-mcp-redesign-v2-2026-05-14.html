1. 现状审视：兜底其实没那么稳

LinDangAgent 在 README/AGENT_GUIDE 里宣传"5 层数据源兜底"（tushare→akshare→东财→baostock→sina），实际 agent 扫代码发现兜底深度因 op 而异、缺口明显。

1.1 兜底深度真相表

工具/op实际兜底层数状态主要问题
gate（退市/ST 闸门）2 层（QMT→Tushare）可接受全挂时返回 UNKNOWN 放行，逻辑合理
basic（基本面）6 层 (QMT→Tushare→akshare→EM→Baostock→Sina)字段降级降到 Sina 层会丢 PE/PB/换手率，"调通了但数据残缺"
price（K线）5 层较稳EM/akshare 列名需要映射，已处理
financial（财报）3 层精度丢失akshare 兜底只提供"财务摘要文本"，缺精确财务表
flow / dragon-tiger / margin（资金面）3 层（Tushare→akshare→EM）还行akshare 字段顺序可能不同，已处理
valuation / northbound / holders / pledge / funds2 层（Tushare→akshare）浅northbound 兜底窗口从 60 日缩到 20 日
peers（同业对比）1.5 层（"假兜底"）骨折Tushare 没数据时退化为"行业名+股票名单"——估值字段完全消失
qmt-kline / qmt-realtime / qmt-sector / qmt-financial1 层（仅 QMT）零兜底QMT 未启动 → 直接异常退出，AI 拿到 error 就停了
indicators（17 项技术指标）复用 price 兜底还行price 拿到了就能算
research / news / announcement不存在缺口研报/新闻/公告完全没接
现状不是"没兜底"，是"兜底深度参差不齐 + 兜底质量不一致"。AI 调到 qmt-realtime 拿不到数据就傻眼，调到 basic 拿到了但缺关键字段——这两种失败更隐蔽，比"完全没兜底"更危险。

1.2 三个核心痛点

  • QMT 系列零兜底：QMT 要桌面客户端启动，4 个相关 op 任何时候 QMT 不在线（早 9 点前、晚 4 点后、用户没开机）就全废
  • peers 假兜底：表面有 fallback 实际退化为"无估值数据的名单"——AI 拿到看似 OK 的结果其实没用
  • 研报/新闻/公告完全缺失：投研深挖单股没消息面信息几乎无法形成完整判断

3. 关键发现：simonlin1212/a-stock-data 怎么处理？

这个项目的存在改变了规划的"性价比账"。

它做的事和我们要做的事高度重合——A 股 + 多源融合 + 研报/新闻/公告/财务/估值全覆盖；它的"6 层架构 · 8 数据源"目标和我们的方案 C 几乎一致；最新版本就在两天前发的（2026-05-12 v2.1.0）。

三个选项要选：

选项怎么做优点缺点
A. 直接 fork + 改名接入 把 simonlin1212/a-stock-data clone 下来当成 LinDangAgent 的子模块或替代品，做最小集成（适配 data_query.py 入口） 1 周内能搞定研报/新闻/公告 + 多源融合；维护成本最低 外部项目弃维风险；许可协议（Apache 2.0 OK 但需保留版权声明）；与现有 QMT 客户端集成需要桥接
B. 只借鉴它的 schema 和数据源选择 ✓ 已选 读它的代码看它用了哪些源（mootdx + Tencent + Eastmoney + akshare + iwencai + Baidu + THS + cninfo），把缺的那些接进 LinDangAgent 完全可控，与现有 LinDangAgent 5 层兜底 + QMT + fetch_warning 机制一致；不背别人项目弃维风险 1-2 周工作量；要重新写适配层
C. 完全不用它，自己从头规划 按方案 C 原计划走，akshare + 自己实现公告爬虫 不依赖任何外部新项目 错失"已有人趟过的雷"的现成经验
我的建议：选 B。理由：
  • LinDangAgent 已经接了 QMT/Tushare/akshare 等 5 层 + 自有 fetch_warning 机制，重写 cost 大于收益
  • 不背别人项目维护风险（哪天作者断更，我们没法快速调整）
  • "借鉴数据源 + schema"成本最低，能拿到对方踩过坑的红利
  • iwencai（同花顺问财）和 cninfo（巨潮）这两个源是亮点——他们已经验证了可用性

4. 兜底链设计原则

三条原则

  1. 主源选"质量最高的"，兜底源选"覆盖率最高的"。例如行情主源用 QMT（最准、有实时盘口），兜底用 Ashare（永远在线、零依赖）
  2. 每条链至少 3 层、关键 op 至少 5 层。"调用一定成功"的核心是层数够 + 每层独立失败概率小
  3. 降级要透明。每次走 fallback，结果里带 fetch_warning="走了 akshare 兜底"，AI 可以在结论里说"数据来源是兜底，可信度略低"
用户原话：以行情为例，应该先 QMT 再 tushare 再 akshare 逐次兜底，确保调用一定成功。这条规则适用于所有工具——主源失败不能让 AI 干瞪眼。

5. stock_market 兜底链

用途：拿实时维度——行情、技术指标、资金流、龙虎榜、北向、融资融券。

行情主链（price / qmt-kline / qmt-realtime）
QMT→ Ashare 🆕→ Tushare→ akshare→ 东财→ Sina→ Baostock

7 层兜底，每层独立请求超时 ≤8s，总超时 ≤60s（绝大多数 case 应在 5-15s 内成功，60s 是 worst case 兜底窗口）。当前主要改动：QMT 之后插 Ashare 作为"客户端不可用时的紧急救场"，零依赖单文件库。

技术指标（indicators）
复用上面 price 兜底→ 本地计算（17 项指标都是纯算）

只要 price 拿到任一层数据，indicators 一定能算。

资金流类（flow / dragon-tiger / northbound / margin）
Tushare→ akshare→ 东财→ efinance 🆕

4 层。efinance 是东财的封装，作为东财直连失败时的补救。

QMT 是最权威的实时行情源（盘口+逐笔），但它要求桌面客户端启动。Ashare 用新浪/腾讯公开 HTTP 接口（自己双源切换），永远在线——QMT 不可用时这是唯一无门槛的实时行情源。

6. stock_static 兜底链

用途：拿慢变维度——闸门、基本面、财报、估值、同行、股东、质押、基金、研报。

基本面（basic）
QMT→ Tushare→ akshare→ 东财→ adata 🆕→ Baostock→ Sina（字段降级）

7 层。adata 内建多源切换，作为中部稳定档。最后 Sina 层注明"字段不全"，AI 能感知到。

财报（financial）
Tushare→ QMT→ adata 🆕→ akshare（摘要）→ cninfo 🆕

5 层。补强重点：原来 akshare 之后断了，现在末层加 cninfo（巨潮公告里的财报附件，硬数据源）。

同业对比（peers，假兜底 → 真兜底）
Tushare 估值→ akshare 行业估值 🆕→ 东财行业资金 🆕→ 本地名单（带降级标记）

4 层。修复假兜底：之前 Tushare 失败就直接退化为"只有名单没估值"。新增中间两层（akshare 行业估值 + 东财行业资金），尽量保住估值字段。

研报（research）🆕 全新
akshare stock_research_report_em 🆕→ iwencai 同花顺问财 🆕→ 东财研报页 🆕

3 层。主源 akshare 内置接口，零 token。iwencai 是 simonlin1212 验证过的副源。

其他慢变（valuation / holders / pledge / funds）
Tushare→ akshare→ adata 🆕→ 东财 🆕

4 层（之前都是 2 层）。adata + 东财补到中间。

慢变维度的字段质量比可用性更重要——所以前几层是"高质量精确数据"（Tushare/QMT/adata），最后才走纯爬虫兜底。AI 拿到的数据宁可少几个字段也别瞎编。

7. stock_news 兜底链 🆕

用途：拿消息面——个股新闻、公司公告。

新闻（news）
akshare stock_news_em 🆕→ 东财个股新闻直连 🆕→ 百度股市通新闻 🆕→ 新浪财经个股 🆕

4 层。主源 akshare 东财接口，副源依次降级到 web 爬虫。

公告（announcement）
akshare stock_notice_report 🆕→ cninfo 巨潮 🆕→ 交易所官网 sse/szse 🆕→ 东财公告页 🆕

4 层。巨潮是公告权威源，作为副源很合适。

公告必须有，因为它是法定披露——公司任何重大事项都强制走公告（不像新闻可以选择性报道）。AI 看不到公告就少了"公司自己说了什么"这条核心信息。

8. 关键决策（✅ 已确认 · 2026-05-14）

#问题决策落地含义
1 simonlin1212/a-stock-data 怎么处理 B 借鉴 schema 和数据源 不直接 fork。仅参考其数据源选择（mootdx / iwencai / cninfo 等）和工具命名规范，落地到 LinDangAgent 现有架构
2 mootdx 弃维风险 A 副源保留 放兜底链中后段，能用就用；不可用时 fallback 直接跳过到下一层；主链不依赖
3 pysnowball 雪球情绪 不做 v1 不引入。先把硬数据（研报/新闻/公告）做扎实；舆情未来再说
4 每条兜底链总超时 60s 统一 三个工具一致：stock_market / stock_static / stock_news 都 ≤60s。每层独立超时调到 ≤8s，最坏 7 层兜底也能 60s 内闭环
5 cninfo 巨潮公告爬虫 A 引入，放兜底中段 akshare 公告接口主源，cninfo 作为副源；接受偶发反爬失败 fallback 到下一层
5 项决策的合力效果：方案完全可控（不背 fork 外部项目的维护风险） · 覆盖完整（akshare 三接口 + cninfo 补足研报/新闻/公告硬数据） · 兜底充足（每层 ≤8s × 最多 7 层 ≤ 60s，常态 5-15s 内成功） · 范围聚焦（情绪/舆情等软数据留到 v2）。

9. 风险与取舍

已识别风险

  • 兜底层数增加会拖慢调用：原本 1 层调用 ~1s，7 层最坏情况 ~7s。缓解：每层独立超时 ≤5s，且只有真失败才降级（不要"每层都试一遍取最好的"）
  • 新增 4-5 个外部 Python 库依赖：Ashare/adata/efinance/mootdx/akshare-one。缓解：单文件库（Ashare）直接 vendor 进 LinDangAgent；大库走 requirements.txt + 版本钉死
  • cninfo / iwencai 爬虫脆弱：网站改版会挂。缓解：放兜底链中后段，主源用 akshare 内置接口（akshare 维护者会跟改版）
  • fetch_warning 暴增：每次兜底都记录 warning，多了 AI 容易过度解读"数据不可信"。缓解：warning 分级——"主源切副源"是 INFO，"切到末层"才是 WARN
  • simonlin1212/a-stock-data 是新项目：v2.1.0 才发了两天，社区验证少。缓解：选 B 借鉴而非 fork，不背它的维护风险

9.1 主动放弃

  • 暂不接入 pysnowball（情绪/舆情侧）—— v1 先做硬数据
  • 暂不实现"跨股对比"工具 —— 让 AI 多次调 stock_static 即可
  • 暂不接入财联社电报 —— 反爬严重，不值得
  • 暂不做"选股/筛选/排序" —— 用户已确认主场景是单股深挖
