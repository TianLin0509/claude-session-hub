# 请公司 CodeAgent 办事（特战队团队版）

> 由 AI HUB 随家里端安装（用邀请码接入的电脑才装）。你自己改过这个文件，Hub 以后就不会再覆盖它。

## 定位

- 你（家里的 Agent）负责想法、方案、判断和实现。公司 CodeAgent 是一位在公司电脑上替你跑腿的同事：模型能力弱于你，一个来回通常 5–15 分钟。它的回执是证据，不是结论，由你核对后再采用。
- 它能做：读公司代码；按目录、文件名、关键词查公司电脑上的文件和文档；运行查询类命令（如 `git log`、`dir`、`findstr`）；查看本机环境和配置；用公司电脑上注册的 MCP。
- 有副作用的动作（提交或运行仿真、同步工程、发消息）它只在你明确要求时才做：需要时在任务单里写明「请运行……」，并说清参数和期望结果。
- 它不做：修改、新建、删除公司电脑上的文件，提交代码，安装软件；回执里不放成段源码、账号密钥这类凭据和与问题无关的个人信息。这些靠给它的说明约束，所以任务单里不要提出这类要求。需要时换成「讲清逻辑」「告诉我在哪个文件第几行」「列出名字和用途」。
- 每个编号对应公司一个独立会话：同一件事的追问进同一个会话，它记得上一轮做过什么；不同的事互不干扰。

## 什么时候用

- **用户点名时**：用户说「问一下公司的 CodeAgent」「让公司那边查一下 xxx」「看看公司电脑上……」，照办，不限话题。把用户的原意整理成自包含的任务单再发。
- **自己主动时**：只在「答案取决于公司代码的实际写法，本地仓库、文档和你的知识都给不出可靠答案」时发问。值得问的例子：公司实现里某个参数的取值、默认值或更新时机；某个流程的分支条件和先后顺序；家里实现与公司实现是否一致、差在哪；某个接口的输入输出定义。
- **先不问**：通信原理、3GPP 条文、本地能查到的内容、只是想「再确认一下」的事。主动发问时一个任务通常 0–2 次，把同一任务的疑问攒成一份清单一次问完。
- 要公司跑仿真、编译或改代码时，任务单里写清步骤、参数和**遇阻即停**：笼统写「必要的生成和编译」曾把远端工程编坏过。
- 只读调查同样写明遇阻即停和本轮时间上限（一般 15 分钟）：查不到、报错就先回报已有结果，不要一直挣扎到会话被关、家里什么也收不到。

## 怎么发

会话里有 MCP 工具 `ask_company` 时用它；没有时在 shell 里用命令。命令的位置由 AI HUB 写在环境变量 `HUB_BRIDGE_CLI` 里（只有家里和公司配对后、由 Hub 打开的会话才有）：

```powershell
node "$env:HUB_BRIDGE_CLI" ask --file <任务.md> --title "<20 字内的标题>" [--model <公司模型表里的模型名>]
```

在 Git Bash 里写作 `node "$HUB_BRIDGE_CLI" ask --file <任务.md> --title "..."`。环境变量不存在，说明这个会话不能联系公司：告诉用户需要在 Hub 里新开（或重开）一个会话；主动发问的场景则按现有证据继续，并在汇报里写明待公司核实的点。

### 选模型（`ask_company` 有 `model` 参数时才用）

- 先看公司模型表：MCP 的 `ask_company` 描述末尾就是（模型名、哪个是日常主力、几个号、还能并行几个、公司现在是不是忙时）；命令行用 `node "$env:HUB_BRIDGE_CLI" models`。
- 简单查询、定位、只读一两个文件 → 非主力或空闲的模型；跨模块推理、算法细节核对 → 日常主力；工作日忙时简单任务优先给非主力模型。拿不准就不填，用公司默认。
- 模型名要和表里一致，写错会直接报错并列出可选项。追问沿用原会话的模型，不用再填。模型表显示「未知」时不填。

### 任务单

写成自包含的 Markdown，对方看不到你的上下文：

1. 目的：一句话说明在做什么、为什么要公司那边的信息。
2. 要做的事 / 要问的点：编号列出，每点一个能验证的结果。
3. 已知线索：家里现在的做法（关键参数、公式或流程）、建议去看的目录、模块、函数名或关键词；不确定就写你的猜测。
4. 回复要求：先结论，按编号逐条回答；标出把握程度和没读到的部分；需要篇幅限制时写明。
5. 要对方回传**数据**（表格、采样值）时写明格式：用 Markdown 表格行（每行以 `|` 开头和结尾），**不要放进代码围栏**，中转会把超过 3 行的代码块当源码整段删掉；单次回执约 2 万字上限，超了按行分轮发；每轮表后附 rows / cols / sum 供家里核对。

## 发出之后

- 工具立刻返回编号（如 `Q-1015-01`）。回执到达后，Hub 会把它作为一条新消息自动发回本会话。
- 发出后结束本轮，或先做不依赖回执的部分。等待交给 Hub，不要循环查询或 sleep。
- 把编号写进进度说明和报告，方便追溯。

## 收到回执后

- 逐条核对：和家里的证据、协议、常识是否一致；它说的是「读到了 / 实际运行看到了」还是「推测」；把握程度如何。
- 可信就采用，并注明依据的编号。
- 存疑就追问：`followup_company`，或 `node "$env:HUB_BRIDGE_CLI" followup --thread Q-xxxx --file 追问.md`。指出哪里不可信、请它再看哪里。次数不限，每次追问都比上一次更具体。
- 公司报错或迟迟没有回执（公司电脑可能离线或在等网络放行）：告诉用户，并按现有证据继续。用 `company_thread`（或 `node "$env:HUB_BRIDGE_CLI" show`）看进度。
- 回执报「没答上」，或发出 20 分钟以上还没有回执：先用 `recollect_company`（或 `node "$env:HUB_BRIDGE_CLI" recollect --thread Q-xxxx`）补收，公司直接取回那个会话里已经写好的最新回答，不重答；取不到再用 followup 重问。

## 公司 Hub 的状态与更新

- 用户问「公司电脑怎么样」「公司 Hub 什么版本」时用 `company_diag`（秒级，不经 CodeAgent）或 `company_hub_update op=status`。
- 用户说「让公司 Hub 更新 / 重启」时用 `company_hub_update`（`op`：`update` / `restart` / `status`）。调用后立即返回指令编号，进度以 Hub 通知送达，不要循环等待。也可以在家里 Hub 无线页「公司联动」里点按钮。

## 底线

- 不要求对方发送源码、密钥、账号、主机名或人员信息。
- 回执只用于理解逻辑、核对差异、了解公司那边的情况，不把其中内容原样搬进家里的代码。
